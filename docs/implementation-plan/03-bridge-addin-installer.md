# Package P3 — Thin Desktop Bridge, Add-in Adaptation, Workstation Installer/Uninstaller, Bridge Self-Update (O9)

## (a) Scope & non-goals

**In scope**

1. A new **thin desktop Bridge** (target-arch Section 5.4): Windows service on designer workstations; outbound WSS primary plus capability-gated Streamable HTTP/SSE fallback to the Gateway (D3, RES-25), local TCP client to the existing C# add-in socket server; invocation execution, idempotency journal, batch→transaction-group pass-through, doc-context watcher, heartbeat, structured logging, enrollment with device token.
2. **Minimal add-in adaptation** (Section 9: adapted, not rewritten): loopback binding, framing standardization, one new composite `execute_batch` command, one new cached `get_document_context` command, two small concurrency fixes. The 21 commands in `src/revit-plugin/revAgentCommandSet/` and the SDK-based dispatch (`SocketService`/`RevitCommandRegistry`) are otherwise untouched.
3. The **new workstation installer** (bridge service + add-in DLLs + `.addin` manifest + enrollment) and the **cutover uninstaller** implementing E4's wipe list (legacy NAS/updater removal plus attested removal of the managed local Codex MCP registrations).
4. **O9 bridge self-update**: gateway-hosted signed version manifest (reusing the existing RS256 detached-signature tooling in `installer/lib/RevAgent.DistributionIntegrity.psm1`), staged rollout, download-verify-swap-restart, crash-loop rollback, and post-cutover delivery of add-in payload updates through the bridge (the "bridge is the last fleet-pushed component" invariant).
5. Replacement of the legacy local ChatGPT/Codex Desktop stdio/NAS registrations at cutover with the selected client's remote MCP registration to the Gateway north surface. Under RES-23, the existing authorized ChatGPT/Codex Desktop application remains the Phase-1 agentic-loop client; only its obsolete workstation-local MCP path is removed. WP9 owns hands-on conformance and the remote-registration instructions.

**Non-goals**

- The Gateway itself, the Bridge↔Gateway protocol *specification* (O1 is a separate deliverable this package consumes; P3 implements the bridge side of it), auth/tenant data model (O3), web client (O8), APS plane (O4).
- No new Revit tools or tool behavior changes (feature freeze, Section 8). The 21 add-in commands, the duct-routing engine, and the TCP length-prefixed framing survive unchanged in function (Section 9).
- The Node/TS MCP runtime (`installer/runtime-mcp-server/`) is **not** ported by this package — it relocates to the Gateway under the Gateway package (Section 8 step 1). P3 only ports workstation-local Revit-client behaviors: length-prefixed framing, bounded loopback discovery, defense-in-depth per-session queueing, and failure-path diagnostics. It does **not** port the legacy per-invocation `mcp_status` busy preflight or the unwritten `%TMP%\revAgent-instances.json` registry read (RES-10, RES-17).
- The second MCP server `installer/revit-api-docs-mcp/` does not move into the bridge; it becomes a gateway-internal executor (registry `executor: internal`, Section 5.2.4). On workstations it is simply wiped (it lives inside `ProgramData\DPE\revAgent\package\`, per E4 §1.1).
- Do not re-open D1–D12 or RES-23/RES-25. In particular D4: Bridge↔Gateway is internal RBP (not MCP); Add-in↔Bridge keeps existing TCP framing. The remote MCP registration belongs to the selected ChatGPT/Codex Desktop client at the Gateway north boundary, never to the bridge.

## (b) Plan-level design decisions

### Bridge technology choice

| Criterion | .NET 8 self-contained Windows service | Node-packaged exe (SEA/pkg) | Go |
|---|---|---|---|
| Team skills (C# + TS) | Native — same language as add-in; can share source with `revAgentPlugin` via netstandard2.0 | Native — same language as current runtime | New language, new toolchain |
| RBP WSS primary + HTTP/SSE fallback; local TCP in | `ClientWebSocket` + `HttpClient` + `TcpClient` built-in | `ws` + `fetch` + `net` built-in | stdlib + 3rd-party WS |
| Windows service lifecycle | First-class: `Microsoft.Extensions.Hosting.WindowsServices` (`UseWindowsService()`), SCM stop/pause, Event Log | Weak: needs NSSM/WinSW/node-windows wrapper — an extra fleet-managed binary, exactly what we are eliminating | Good (`golang.org/x/sys/svc`) but hand-rolled hosting |
| Single-file deploy | Native (`PublishSingleFile` + self-contained, ~35–60 MB) | `pkg` unmaintained; Node SEA still rough (native modules, sqlite) | Best (smallest static exe) |
| Self-update mechanics | Rename-swap of one exe; version-folder + launcher pattern well understood | Wrapper + snapshot FS complicates swap/verify | Simple |
| **Signature verification reuse** | **Direct**: the existing envelope uses `RSACryptoServiceProvider.FromXmlString` + RSA-SHA256 + canonical JSON (`installer/lib/RevAgent.DistributionIntegrity.psm1:243-325`) — all .NET-native APIs; verification is a port, not a reimplementation | Must reimplement RSA XML key parsing + canonical JSON in JS | Must reimplement in Go |

- **P-BRIDGE-1 — Bridge = .NET 8 self-contained single-file Windows service.** Rationale: only option with first-class Windows-service hosting *and* drop-in reuse of the fleet's existing RS256 XML-key/canonical-JSON signature scheme, in the language the add-in already uses.
- **P-BRIDGE-2 — Two-binary host/worker layout for self-update.** Service registration points at a tiny stable `revagent-bridge-host.exe` that launches `versions\current\revagent-bridge.exe` as a child and supervises it; updates swap the worker without ever touching the SCM registration or the running host. Rationale: eliminates the "service must replace its own running exe" problem and gives the host a natural place for crash-loop detection/rollback (P-UPD-4).
- **P-BRIDGE-3 — Idempotency journal = SQLite (WAL mode), one DB file per machine.** The logical key is the RES-21 string `rsid + "/" + invocation_id`; invocation rows retain `params_digest`, method/policy/mutation-scope binding, `received|executing|completed|failed|guarded|cancelled|indeterminate` state, terminal outcome or digest, and any `verification_hold_id`. A distinct durable hold relation retains `(rsid, scope_jcs)`, ordered origin keys, `active|evidence_recorded|resolved_pending_bridge|cleared` state, verification evidence, and resolution metadata. `received` is durable before the first add-in byte; `executing` is durable before dispatch ownership; terminal state is durable before the RBP outcome is sent. A possibly dispatched mutation with no durable terminal outcome becomes `journal_indeterminate` and blocks only later mutations whose server-authored scopes conflict. A correlated verification read records evidence but does not clear the hold by itself; late terminal evidence also does not auto-clear it. The Gateway authors a complete `recovery_clearances` resolution, and the bridge matches that resolution to its durable hold/evidence and atomically marks the hold cleared with acceptance of the new invocation before any add-in byte. Terminal retention defaults to 14 days and must cover every resume/redelivery window; non-terminal rows and uncleared holds are never pruned merely to satisfy a row cap. Rationale: this implements O1/RES-21 rather than the earlier generic `inflight|succeeded|failed` sketch.
- **P-BRIDGE-4 — The Gateway dispatcher owns authoritative one-in-flight-per-`rsid` serialization; the bridge queue is defense-in-depth.** The bridge keeps a `SemaphoreSlim(1)` per registered session so a defective or stale peer cannot race the add-in, but it rejects a second concurrent invocation as an RBP `protocol` fault instead of treating the queue as the authority. The legacy hot-path `mcp_status` preflight is deleted (RES-10): ordinary invokes go directly through the journal and queue. `mcp_status` remains available only for heartbeat snapshots and optional failure-path enrichment after an invocation has failed or timed out.
- **P-BRIDGE-5 — Doc-context watcher = cheap cached snapshot poll, not ExternalEvent round-trips.** The add-in subscribes to `DocumentOpened/DocumentClosed/ViewActivated` app events at startup, maintains a thread-safe context snapshot, and serves a new `get_document_context` request **from cache on the socket thread** (no ExternalEvent, no UI-thread cost, same pattern as the existing registry-bypassing `mcp_status` special case at `SocketService.cs:522-526`). Bridge polls it every 15 s + immediately after registration/resume, normalizes and diffs the snapshot, and emits the exact O1 data envelope `{type:"doc_context_update",rsid,seq,payload}` only when it changes. The frozen payload is `{documents:[{document_id,title,path_digest,is_workshared,is_active}],active_document,active_view:{id,name,type,level?}|null,discipline_hint?}`; raw model paths never replace `path_digest`. Positive/null/negative golden vectors are generated and validated against the frozen O1 `common.schema.json`, `payloads.schema.json`, and `envelope.schema.json` before M3 implementation merges. Rationale: RES-3 needs continuously available document context without burning ExternalEvent slots by polling `list_open_views`/`get_current_view_info`.
- **P-BRIDGE-6 — New shared `netstandard2.0` project `packages/bridge/src/RevAgent.Contracts/`** holding: frame codec (4-byte big-endian length prefix, mirroring `SocketService.cs:336-367,446-468` and `SocketClient.ts:396-406`), JSON-RPC request/response models, the frozen RBP/1 `display` shape and its explicit mapper, and the signature-envelope model + verifier. The frozen schema defines six known optional snake_case properties—`task_name`, `wrapper_action`, `logical_tool_name`, `parent_task_name`, `parent_task_id`, and `suppress_task_status_window`—while permitting additive unknown properties for within-version compatibility. The add-in hop recognizes the corresponding six camelCase side-channel keys (`taskName`, `wrapperAction`, `logicalToolName`, `parentTaskName`, `parentTaskId`, `suppressTaskStatusWindow` — `SocketService.cs:539-547`). The mapper allowlists and maps only those six known properties, preserves the two nullable parent fields and omitted optional values, and never forwards an unknown additive RBP property or a raw snake_case key into add-in params. Golden vectors pin all six mappings, null/omitted variants, and unknown-field non-forwarding against the frozen O1 schemas. The project joins `packages/bridge/RevAgent.Bridge.sln` immediately and is consumed by the net8 bridge; the net48 add-in reference lands only with P3-T6's bounded freeze exception. Rationale: DP-13 keeps all new Bridge work under `packages/bridge`, one framing implementation replaces three, and RevitMCPSDK types stay untouched.
- **P-BRIDGE-7 — One RBP state machine, two Phase-1 bindings.** WSS is primary. The capability-gated Streamable HTTP/SSE fallback carries identical hello/session/sequence/ack/resume/journal messages and reconnects through the same durable state; it never silently switches an active WSS connection in place. Both bindings honor system proxy and machine trust, and neither may enter pilot use until the O1 frozen binding plus proxy/interoperability vectors are green (RES-25).

### Add-in adaptation (minimal, per E2)

- **P-ADDIN-1 — Bind the TCP listener to loopback with no production opt-out.** `TcpListener(IPAddress.Any, port)` at `SocketService.cs:157` becomes `IPAddress.Loopback`. No environment, configuration, hostname, wildcard, LAN, or remote override may widen the listener or bridge target; a non-loopback candidate is rejected and audited before any JSON-RPC byte. Rationale: the bridge is local; an unauthenticated all-interfaces socket is an unnecessary exposure the target's zero-trust NFR (Section 6) does not tolerate, and O1 loopback-only conformance is mandatory.
- **P-ADDIN-2 — Length-prefixed framing only; legacy path retired on a config gate.** Keep `DetectMessageFraming` (`SocketService.cs:416-439`) through the pilot; the bridge never sends `LegacyJson`; remove detection + the client fallback logic one release after cutover (O1 note in E2). Rationale: dead compatibility shim once the Node runtime leaves the workstation.
- **P-ADDIN-3 — New `execute_batch` command in `revAgentCommandSet`** implementing the exact frozen O1 Appendix A.2/A.4 batch primitive. The request carries the ordered raw step params plus `batchId`, `batchDigest`, per-step `invocationId`/`paramsDigest`/`effect`, and the negotiated `maxAggregateResultBytes`; every admitted step must match the latest session-local `batchableCommands` descriptor with `resultDelivery:"inline_only"` and `maxInlineResultBytes:8388608`. `execute_batch`, `mcp_status`, raw dynamic code, and the frozen UI-interactive exclusions cannot be nested. The Appendix A.4 reserved-name set is rejected before dispatch, and no nested step may raise or wait for another `ExternalEvent`. The event handler validates the complete carrier before opening one `TransactionGroup`, invokes the extracted command seams directly on the Revit API thread, projects each tentative response before `Assimilate()`, and rolls back on the first guarded/failed/invalid-result/per-step-or-aggregate delivery violation. It returns the frozen transaction/effect-state matrix; it never creates a chunk/artifact carrier for a nested step. The bridge passes an atomic Gateway batch as **one** length-prefixed framed request and fails closed on a contradictory response. Rationale: N round-trips → 1 and atomicity live where the Revit API lives; RES-26 delivery safety is enforced before commit and the bridge stays thin. `batch_execute` is not an RBP/1 command name.
- **P-ADDIN-4 — Fix the two concurrency defects E2 identified while we are in the file:** (1) `ExecuteCodeEventHandler.WaitForCompletion` resets `_resetEvent` *before* waiting (`ExecuteCodeEventHandler.cs:43-47`), which can drop an already-signaled completion — move the `Reset()` to before `Raise()`; (2) add a global intake single-flight lock in `SocketService.ProcessJsonRPCRequest` so concurrent connections cannot race singleton command handler parameter state (today only some commands defend, e.g. `GetSelectedElementsCommand._executionLock` at line 16 vs. none in `ExecuteCodeCommand`). Rationale: cheap defense-in-depth even though the bridge serializes (P-BRIDGE-4).
- **P-ADDIN-5 — Preserve add-in port allocation; replace client discovery authority.** The add-in keeps env → `commandRegistry.json` → 8080 and +20 conflict allocation (`SocketService.cs:86-109,149-185`). The bridge first validates an explicit configured loopback target, otherwise performs the bounded 8080–8085 scan and accepts a candidate only after an `mcp_status` shape/version probe. It never reads `%TMP%\revAgent-instances.json` because no production writer exists (RES-17), and it rejects LAN, wildcard, or hostname-resolved non-loopback targets before sending JSON-RPC bytes. Every accepted process is registered as a distinct routable Gateway session.

### Enrollment

- **P-ENROLL-1 — Two-token enrollment: short-lived enrollment token at install, long-lived device token thereafter.** Installer accepts `-EnrollmentToken` (minted by an admin in the Gateway dashboard/CLI, single-use, TTL ≤ 24 h, per O3's device table); on first start the bridge exchanges it for a device token bound to `(tenant, machine fingerprint)`; device token stored DPAPI-protected (LocalMachine scope) under the bridge state root, never in config files. Seat check happens at Gateway connection time (Section 5.1.4), not in the bridge. Rationale: keeps cutover-night install scriptable (~12 machines, one token batch pre-minted) with no interactive browser flow on workstations; user identity (OIDC) rides the chat/MCP clients, not the bridge.

### O9 self-update

- **P-UPD-1 — Manifest signed with the existing detached RS256 envelope semantics; new WP3-owned `signedObject` kind `bridge-manifest`.** `installer/lib/RevAgent.DistributionIntegrity.psm1` is a frozen, read-only compatibility oracle: WP3 MUST NOT edit its allowlist, validator, or any other byte. A dedicated signer under `packages/bridge/` uses the pinned production key `revagent-prod-rsa-2026q3` (`scripts/publish-signed-source-free-release-to-nas.ps1:89`) from `C:\ProgramData\DPE\revAgentReleaseSigning\private` and emits the same XML-key/fingerprint, canonical-JSON, `contentSha256`, and RSA-SHA256 contract. The signed bytes are the exact nine-field canonical projection `{schemaVersion,app,signedObject,algorithm,keyId,publicKeyFingerprint,canonicalization,contentSha256,createdAtUtc}`; the envelope's `signature` field is omitted from that projection rather than serialized as an empty field. The bridge verifies that envelope through the C# port in `RevAgent.Contracts`; parity tests consume positive and negative fixtures produced by the frozen PowerShell implementation without importing or modifying it. Trusted keys are pinned in the Bridge artifact and may be superseded only by an independently signed trusted-keys document under the existing rotation rules. Rationale: E4's explicit finding — the signing tree survives cutover precisely to serve O9; no new crypto scheme, no new key ceremony, and no mutation of the rollback-critical installer module.
- **P-UPD-2 — Manifest content and rollout gating.** Gateway serves `GET /bridge/update/manifest` (device-token-authenticated): `{schemaVersion, channel, version, releaseSequence, components:[{name: bridge|addin, version, sha256, sizeBytes, url}], rolloutPercent, minSupportedVersion, notes}` + detached `bridge-manifest` envelope. Staged rollout: bridge applies iff `SHA256(deviceId) mod 100 < rolloutPercent`, with a Gateway-side per-device ring override so the pilot machine is always ring 0. Anti-rollback: bridge persists `highestAcceptedReleaseSequence` (same semantics as today's updater state in `updater\installed.json`, E4 §1.1) and refuses manifests with a lower sequence; `minSupportedVersion` lets the Gateway force-refuse sessions from too-old bridges at handshake (O1). Artifacts live in Gateway object storage (Section 5.9). Rationale: percentage + rings reproduces the current pilot→stable channel discipline (`channels\stable` pairs, `publish-signed-source-free-release-to-nas.ps1:1770`) without the NAS.
- **P-UPD-3 — The bridge is the fleet's *only* updater post-cutover, including for the add-in payload.** Manifest `components` includes the add-in DLLs; the bridge stages them and applies **only when no Revit process holds the target DLLs** (same deferral rule the current updater documents — "Revit-loaded payload updates are deferred while Revit is open", `installer/nas/install-updater-task.ps1:2709`), retrying at heartbeat cadence and reporting "staged/applied/deferred" state to the Gateway (visible in the dashboard, Section 5.10). This operationalizes the invariant: the workstation installer (P3-T9) is the last fleet push ever; afterwards every workstation byte (bridge worker + add-in payload) flows through signed manifests. Rationale: without this, add-in fixes would silently re-create a fleet-push channel and break D11's end state.
- **P-UPD-4 — Download-verify-swap-restart with crash-loop rollback in the host.** Sequence: download to `staging\` → verify sha256 per component → verify manifest envelope → move to `versions\<ver>\` → flip `current` junction → host gracefully stops worker (worker drains: finishes in-flight invocation or journals it, closes WSS with resume token) → host starts new worker. Rollback: if the worker exits abnormally ≥3 times within 5 minutes of a version flip, the host reverts `current` to the previous version directory, marks `<ver>` quarantined in local state, and reports the event to the Gateway on next connect (dashboard alert + automatic rollout-percent freeze is a Gateway-package follow-up). Two version directories retained minimum. Rationale: Section 5.4's self-update duty with the same "old path restorable" iron rule (Section 8) applied at machine granularity.

## (d) Test strategy

1. **Golden-vector compatibility tests (cross-implementation).** The frame codec and signature verifier are ports of proven code; both get byte-exact fixtures: frames captured from the live Node client/add-in pair, and signature envelopes generated by the read-only `installer/lib/RevAgent.DistributionIntegrity.psm1` oracle (reusing the negative vectors from `scripts/test-distribution-integrity.ps1:441-449` — unknown key, wrong fingerprint). Schema-derived vectors separately pin the six known optional RBP `display` properties, their allowlisted mapping into the six-key add-in side-channel namespace, null/omitted behavior, unknown additive-field non-forwarding, and exact positive/null/negative `doc_context_update` data envelopes. CI runs these on the Windows runner (`ci.yml` already builds the plugin there).
2. **Live add-in integration** on the existing Windows runner/dev machine with Revit 2022: extend `scripts/test-commandset-live.ps1` conventions with a bridge-driven variant — all 21 commands + `execute_batch` + `get_document_context` invoked through the bridge instead of the Node runtime. Assert that ordinary invokes emit no `mcp_status` preflight and discovery reads no temp registry. This is the primary regression gate proving Section 9's "add-in adapted, not rewritten".
3. **Fault injection is first-class, not incidental** (P3-T13): the bridge's whole reason to exist is flaky-link correctness. Mandatory scenarios: link kill mid-invocation, redelivery after resume, duplicate batch delivery, bridge process kill mid-write (journal recovery), machine sleep/wake, Gateway restart (session resume from store), add-in restart mid-session (Revit closed/reopened).
4. **Self-update drills as automated tests** (P3-T11 acceptance list): every negative path (tamper, downgrade, crash-loop) is a scripted VM test, not a manual checklist — mirroring the house style of `scripts/test-signed-source-free-cd.ps1`.
5. **Installer/uninstaller matrix on VM snapshots**: snapshots provisioned with the real current stack (installer + updater task + dashboard addon + usage-intelligence addon + Codex integration) so the wipe list is tested against reality, including byte-identical/hash-verified preservation of the ACL-protected `bootstrap\`, `prestage\install-revagent-local-bootstrap.ps1`, and `updater\config\release-trusted-keys.json` anchors plus the keep-list guard for coordinator/signing hosts. Dry-run and committed runs assert that no ownership or content change reaches those anchors and that the only user-owned Codex-config mutation is removal of the exact two managed legacy local MCP sections; `AGENTS.md`, skills, PowerShell profiles, and every other config entry remain unchanged. No PowerShell on the Linux CI box — these run on the self-hosted Windows runner or a dedicated test VM, consistent with existing practice.
6. **Static analysis on Linux CI** limited to the .NET build, unit tests, and contract fixtures; anything touching Revit, services, or ACLs runs on Windows.
7. **Transport parity is a Phase-1 gate.** The same scripted disconnect/resume/journal corpus runs over WSS primary and Streamable HTTP/SSE fallback through the proxy lab. It proves equal sequence/ack/redelivery outcomes, capability-gated fallback selection, and no active WSS in-place switch.
8. **Pilot = the final test** (Section 8 step 2): a few days of real design work on one workstation using the WP9-proven ChatGPT/Codex Desktop remote MCP registration, exercising reconnects, self-update, and serial/guarded semantics before fleet cutover. The legacy local stdio/NAS path remains absent throughout.

## (e) Risks specific to this package

| # | Risk | Mitigation |
|---|---|---|
