# Package P3 — Thin Desktop Bridge, Add-in Adaptation, Workstation Installer/Uninstaller, Bridge Self-Update (O9)

## (a) Scope & non-goals

**In scope**

1. A new **thin desktop Bridge** (target-arch Section 5.4): Windows service on designer workstations; outbound WSS to the Gateway (D3), local TCP client to the existing C# add-in socket server; invocation execution, idempotency journal, batch→transaction-group pass-through, doc-context watcher, heartbeat, structured logging, enrollment with device token.
2. **Minimal add-in adaptation** (Section 9: adapted, not rewritten): loopback binding, framing standardization, one new composite `batch_execute` command, one new cached `get_document_context` command, two small concurrency fixes. The 21 commands in `src/revit-plugin/revAgentCommandSet/` and the SDK-based dispatch (`SocketService`/`RevitCommandRegistry`) are otherwise untouched.
3. The **new workstation installer** (bridge service + add-in DLLs + `.addin` manifest + enrollment) and the **cutover uninstaller** implementing E4's wipe list (old NAS/updater/Codex stack removal).
4. **O9 bridge self-update**: gateway-hosted signed version manifest (reusing the existing RS256 detached-signature tooling in `installer/lib/RevAgent.DistributionIntegrity.psm1`), staged rollout, download-verify-swap-restart, crash-loop rollback, and post-cutover delivery of add-in payload updates through the bridge (the "bridge is the last fleet-pushed component" invariant).
5. Removal of the ChatGPT/Codex desktop MCP integration at cutover (per E4 findings), with the *option* of later reconnection to the Gateway's north MCP surface documented but explicitly deferred.

**Non-goals**

- The Gateway itself, the Bridge↔Gateway protocol *specification* (O1 is a separate deliverable this package consumes; P3 implements the bridge side of it), auth/tenant data model (O3), web client (O8), APS plane (O4).
- No new Revit tools or tool behavior changes (feature freeze, Section 8). The 21 add-in commands, the duct-routing engine, and the TCP length-prefixed framing survive unchanged in function (Section 9).
- The Node/TS MCP runtime (`installer/runtime-mcp-server/`) is **not** ported by this package — it relocates to the Gateway under the Gateway package (Section 8 step 1). P3 only *ports the runtime's Revit-client behaviors* that are workstation-local by nature: framing client, busy preflight, serial-execution locking, instance discovery (today in `installer/runtime-mcp-server/src/utils/SocketClient.ts` and `ConnectionManager.ts`).
- The second MCP server `installer/revit-api-docs-mcp/` does not move into the bridge; it becomes a gateway-internal executor (registry `executor: internal`, Section 5.2.4). On workstations it is simply wiped (it lives inside `ProgramData\DPE\revAgent\package\`, per E4 §1.1).
- Do not re-open D1–D12. In particular D4: Bridge↔Gateway is internal RPC (not MCP); Add-in↔Bridge keeps existing TCP framing.

## (b) Plan-level design decisions

### Bridge technology choice

| Criterion | .NET 8 self-contained Windows service | Node-packaged exe (SEA/pkg) | Go |
|---|---|---|---|
| Team skills (C# + TS) | Native — same language as add-in; can share source with `revAgentPlugin` via netstandard2.0 | Native — same language as current runtime | New language, new toolchain |
| WSS out + local TCP in | `ClientWebSocket` + `TcpClient` built-in | `ws` + `net` built-in | stdlib + 3rd-party WS |
| Windows service lifecycle | First-class: `Microsoft.Extensions.Hosting.WindowsServices` (`UseWindowsService()`), SCM stop/pause, Event Log | Weak: needs NSSM/WinSW/node-windows wrapper — an extra fleet-managed binary, exactly what we are eliminating | Good (`golang.org/x/sys/svc`) but hand-rolled hosting |
| Single-file deploy | Native (`PublishSingleFile` + self-contained, ~35–60 MB) | `pkg` unmaintained; Node SEA still rough (native modules, sqlite) | Best (smallest static exe) |
| Self-update mechanics | Rename-swap of one exe; version-folder + launcher pattern well understood | Wrapper + snapshot FS complicates swap/verify | Simple |
| **Signature verification reuse** | **Direct**: the existing envelope uses `RSACryptoServiceProvider.FromXmlString` + RSA-SHA256 + canonical JSON (`installer/lib/RevAgent.DistributionIntegrity.psm1:243-325`) — all .NET-native APIs; verification is a port, not a reimplementation | Must reimplement RSA XML key parsing + canonical JSON in JS | Must reimplement in Go |

- **P-BRIDGE-1 — Bridge = .NET 8 self-contained single-file Windows service.** Rationale: only option with first-class Windows-service hosting *and* drop-in reuse of the fleet's existing RS256 XML-key/canonical-JSON signature scheme, in the language the add-in already uses.
- **P-BRIDGE-2 — Two-binary host/worker layout for self-update.** Service registration points at a tiny stable `revagent-bridge-host.exe` that launches `versions\current\revagent-bridge.exe` as a child and supervises it; updates swap the worker without ever touching the SCM registration or the running host. Rationale: eliminates the "service must replace its own running exe" problem and gives the host a natural place for crash-loop detection/rollback (P-UPD-4).
- **P-BRIDGE-3 — Idempotency journal = SQLite (WAL mode), one DB file per machine.** Schema: `invocations(invocation_id TEXT PK, session_id, tool, params_digest, status {inflight|succeeded|failed}, outcome_json/result_ref, started_at, finished_at)`; redelivered invocation ids answer from the journal (Section 5.4). Rationale: crash-safe atomic writes and indexed lookup beat an append-only JSON file (today's precedent, `updater\installed.json` / `highestAcceptedReleaseSequence`, is fleet-scale fragile); `Microsoft.Data.Sqlite` + bundled `e_sqlite3` works in single-file publish. Journal rows pruned after a retention window (default 14 days) — long enough to cover any reconnect redelivery.
- **P-BRIDGE-4 — Serial-execution ownership moves from the Node runtime into the bridge as an in-process per-Revit-session queue.** E2 finding: today serialization is enforced client-side via a cross-process filesystem lock dir (`revit-mcp-command-locks`, `ConnectionManager.ts:43,276-321`) plus an `mcp_status` busy preflight (`SocketClient.ts:279-304`). The bridge is the *only* local client post-cutover, so a `SemaphoreSlim(1)` per `(host,port)` session replaces the filesystem locks; the `mcp_status` preflight (served without registry dispatch at `SocketService.cs:522-526`) is kept as defense-in-depth and as the source of "busy with task X" errors returned to the Gateway as structured retryable errors.
- **P-BRIDGE-5 — Doc-context watcher = cheap cached snapshot poll, not ExternalEvent round-trips.** The add-in subscribes to `DocumentOpened/DocumentClosed/ViewActivated` app events at startup, maintains a thread-safe context snapshot, and serves a new `get_document_context` request **from cache on the socket thread** (no ExternalEvent, no UI-thread cost, same pattern as the existing registry-bypassing `mcp_status` special case at `SocketService.cs:522-526`). Bridge polls it every 15 s + immediately after reconnect, diffs, and pushes changes to the Gateway in the O1 session-update message. Rationale: Section 5.2 stage 1 needs "open document, active discipline hint" continuously; polling the existing `list_open_views`/`get_current_view_info` commands would burn ExternalEvent slots on the Revit UI thread.
- **P-BRIDGE-6 — New shared `netstandard2.0` project `src/shared/RevAgent.Contracts/`** holding: frame codec (4-byte big-endian length prefix, mirroring `SocketService.cs:336-367,446-468` and `SocketClient.ts:396-406`), JSON-RPC request/response models, the side-channel display params envelope (`taskName|displayName|operationName`, `wrapperAction`, `logicalToolName`, `parentTaskId`, `suppressTaskStatusWindow` — `SocketService.cs:539-547`, to be formalized by O1), and the signature-envelope model + verifier. Consumed by the net48 add-in (`revAgentPlugin.csproj:18` targets net48 for Revit 2022–2024) and the net8 bridge. Rationale: one framing implementation instead of three; the RevitMCPSDK NuGet stays untouched because no SDK type changes (E2 constraint).

### Add-in adaptation (minimal, per E2)

- **P-ADDIN-1 — Bind the TCP listener to loopback.** `TcpListener(IPAddress.Any, port)` at `SocketService.cs:157` becomes `IPAddress.Loopback` (env-overridable escape hatch for one release). Rationale: the bridge is local; an unauthenticated all-interfaces socket is an unnecessary exposure the target's zero-trust NFR (Section 6) doesn't tolerate.
- **P-ADDIN-2 — Length-prefixed framing only; legacy path retired on a config gate.** Keep `DetectMessageFraming` (`SocketService.cs:416-439`) through the pilot; the bridge never sends `LegacyJson`; remove detection + the client fallback logic one release after cutover (O1 note in E2). Rationale: dead compatibility shim once the Node runtime leaves the workstation.
- **P-ADDIN-3 — New `batch_execute` command in `revAgentCommandSet`** implementing the batch primitive (Section 5.2.4): params = ordered list of `{method, params}` sub-invocations restricted to registered commands; the event handler wraps execution in one `TransactionGroup` (assimilate on full success, roll back on first failure), returns per-item results + group outcome. The bridge passes Gateway batch messages through as **one** framed request. Rationale: N round-trips → 1 and atomicity live where the Revit API lives; the bridge stays thin.
- **P-ADDIN-4 — Fix the two concurrency defects E2 identified while we are in the file:** (1) `ExecuteCodeEventHandler.WaitForCompletion` resets `_resetEvent` *before* waiting (`ExecuteCodeEventHandler.cs:43-47`), which can drop an already-signaled completion — move the `Reset()` to before `Raise()`; (2) add a global intake single-flight lock in `SocketService.ProcessJsonRPCRequest` so concurrent connections cannot race singleton command handler parameter state (today only some commands defend, e.g. `GetSelectedElementsCommand._executionLock` at line 16 vs. none in `ExecuteCodeCommand`). Rationale: cheap defense-in-depth even though the bridge serializes (P-BRIDGE-4).
- **P-ADDIN-5 — Keep the port-resolution and multi-instance behavior exactly as-is** (env → `commandRegistry.json` → 8080, +20 auto-increment on conflict, `SocketService.cs:86-109,149-185`); the bridge ports the runtime's candidate scan [8080..8085] + `%TMP%\revAgent-instances.json` registry read (`ConnectionManager.ts:37-42,245-274`) and reports each discovered Revit session to the Gateway as a distinct routable session. Rationale: multiple concurrent Revit sessions per machine already work; don't disturb it.

### Enrollment

- **P-ENROLL-1 — Two-token enrollment: short-lived enrollment token at install, long-lived device token thereafter.** Installer accepts `-EnrollmentToken` (minted by an admin in the Gateway dashboard/CLI, single-use, TTL ≤ 24 h, per O3's device table); on first start the bridge exchanges it for a device token bound to `(tenant, machine fingerprint)`; device token stored DPAPI-protected (LocalMachine scope) under the bridge state root, never in config files. Seat check happens at Gateway connection time (Section 5.1.4), not in the bridge. Rationale: keeps cutover-night install scriptable (~12 machines, one token batch pre-minted) with no interactive browser flow on workstations; user identity (OIDC) rides the chat/MCP clients, not the bridge.

### Installer / uninstaller

- **P-INST-1 — New disjoint install roots:** binaries in `C:\Program Files\revAgent\Bridge\` (admin-owned: `revagent-bridge-host.exe`, `versions\<ver>\revagent-bridge.exe`, `current` junction) and mutable state in `C:\ProgramData\revAgent\bridge\` (journal.db, logs, device token, staged updates, `bridge-config.json` with the Gateway DNS name — never an IP, Section 5.4). Add-in payload stays where the manifest system expects Revit to find it, but under the new root: `C:\Program Files\revAgent\Addin\<RevitVersion>\` + deterministic manifest at `C:\ProgramData\Autodesk\Revit\Addins\<ver>\revAgent.addin` (same manifest identity the current installer owns — `installer/install-self-contained.ps1:632,661-662`). Rationale: complete disjointness from `C:\ProgramData\DPE\revAgent` makes the E4 wipe list safe to execute mechanically and makes rollback ("restore old stack from NAS once", Section 8 step 4) collision-free.
- **P-INST-2 — Installer stays PowerShell (this is the final fleet push), packaged as one signed script + payload ZIP; the uninstaller is a separate idempotent script with a keep-list and a machine report.** Rationale: the team's mature PS installer discipline (ACL patterns in `installer/lib/RevAgent.Permissions.psm1`, manifest handling in `installer/install-self-contained.ps1`) is reused once and then retired with the NAS; an MSI/WiX investment is wasted on a one-shot cutover because all subsequent delivery is bridge self-update (O9).
- **P-INST-3 — Uninstaller implements E4's wipe list verbatim, with explicit keep-list and decision closures:** remove scheduled tasks `revAgent Auto Update` (+ legacy `Revit MCP Auto Update`, `installer/nas/install-updater-task.ps1:34,2712`), `revAgent Dashboard Server`, `revAgent Dashboard Tunnel` (`addons/dashboard/installer/install-dashboard-addon.ps1:16,18`), `revAgent Usage Summary Publish`, `revAgent Codex Session Context Export` (`addons/usage-intelligence/scripts/install-usage-summary-task.ps1:14`, `install-codex-session-export-task.ps1:14`); delete the `C:\ProgramData\DPE\revAgent` tree (taking ownership first — `bootstrap\` and `execution-snapshots\` are SYSTEM/Admin-ACL'd) and legacy roots (`C:\ProgramData\DPE\RevitMCP`, `%LOCALAPPDATA%\revit-mcp-plugin`, `%APPDATA%\Autodesk\Revit\Addins\2022` legacy manifests, legacy dev clones); per-user surfaces per E4 §1.3 (Codex `[mcp_servers.revAgent]`/`[mcp_servers.revAgent-api-docs]` sections only, managed `AGENTS.md` and skill dirs only after marker/hash attestation — reusing the attestation logic pattern from `installer/lib/RevAgent.CodexRegistration.psm1:4050-4084`; PS-profile managed block removal). **Keep:** proxy env vars/registry (machine networking config), `HKCU:\Console` codepage, the system Node MSI in `C:\Program Files\nodejs` (bridge is self-contained per P-BRIDGE-1, so Node is unused but harmless — closing E4's open decision as "leave, deprioritize"), and the two special-machine trees `C:\ProgramData\DPE\revAgentOps\` (coordinator) and `C:\ProgramData\DPE\revAgentReleaseSigning\` (CD runner host — **required** for O9 signing). Uninstaller writes `wipe-report.json` per machine (found/removed/kept/failed per item) for cutover-night verification.
- **P-CODEX-1 — ChatGPT/Codex desktop integration is removed at cutover and not reconnected in Phase 1.** The wipe removes both `[mcp_servers.*]` stdio registrations (they point at the deleted workstation runtime — `RevAgent.CodexRegistration.psm1:3394-3402,3566-3567` — and cannot work post-wipe); Phase-1 clients are the web chat client and/or existing MCP clients against the north MCP surface per O8. A later optional re-registration of the unified ChatGPT/Codex desktop app as an external MCP client of the Gateway (Streamable HTTP + OAuth, D9) is documented as a follow-up, out of Phase-1 scope. Rationale: one client migration at a time; the desktop app would consume the same north surface as any third-party MCP client, so nothing is foreclosed.

### O9 self-update

- **P-UPD-1 — Manifest signed with the existing detached RS256 envelope; new `signedObject` kind `bridge-manifest`.** Extend the allowlist in `New-RevitMcpDetachedJsonSignature` (`installer/lib/RevAgent.DistributionIntegrity.psm1:291`, currently `channel|release-manifest|license-seat`) and in the envelope-shape validator; sign in CI on the `revagent-cd` runner with the pinned production key `revagent-prod-rsa-2026q3` (`scripts/publish-signed-source-free-release-to-nas.ps1:89`) from `C:\ProgramData\DPE\revAgentReleaseSigning\private`. The bridge verifies in C# via a straight port of the verifier (canonical JSON with ordinal-sorted keys, `contentSha256`, RSA-SHA256 over the payload with empty `signature` field, public-key fingerprint check — `DistributionIntegrity.psm1:189-199,267-325,897`), with the trusted-keys document compiled in **and** overridable by a signed trusted-keys file for future key rotation. Rationale: E4's explicit finding — the signing tree survives cutover precisely to serve O9; no new crypto scheme, no new key ceremony.
- **P-UPD-2 — Manifest content and rollout gating.** Gateway serves `GET /bridge/update/manifest` (device-token-authenticated): `{schemaVersion, channel, version, releaseSequence, components:[{name: bridge|addin, version, sha256, sizeBytes, url}], rolloutPercent, minSupportedVersion, notes}` + detached `bridge-manifest` envelope. Staged rollout: bridge applies iff `SHA256(deviceId) mod 100 < rolloutPercent`, with a Gateway-side per-device ring override so the pilot machine is always ring 0. Anti-rollback: bridge persists `highestAcceptedReleaseSequence` (same semantics as today's updater state in `updater\installed.json`, E4 §1.1) and refuses manifests with a lower sequence; `minSupportedVersion` lets the Gateway force-refuse sessions from too-old bridges at handshake (O1). Artifacts live in Gateway object storage (Section 5.9). Rationale: percentage + rings reproduces the current pilot→stable channel discipline (`channels\stable` pairs, `publish-signed-source-free-release-to-nas.ps1:1770`) without the NAS.
- **P-UPD-3 — The bridge is the fleet's *only* updater post-cutover, including for the add-in payload.** Manifest `components` includes the add-in DLLs; the bridge stages them and applies **only when no Revit process holds the target DLLs** (same deferral rule the current updater documents — "Revit-loaded payload updates are deferred while Revit is open", `installer/nas/install-updater-task.ps1:2709`), retrying at heartbeat cadence and reporting "staged/applied/deferred" state to the Gateway (visible in the dashboard, Section 5.10). This operationalizes the invariant: the workstation installer (P3-T8) is the last fleet push ever; afterwards every workstation byte (bridge worker + add-in payload) flows through signed manifests. Rationale: without this, add-in fixes would silently re-create a fleet-push channel and break D11's end state.
- **P-UPD-4 — Download-verify-swap-restart with crash-loop rollback in the host.** Sequence: download to `staging\` → verify sha256 per component → verify manifest envelope → move to `versions\<ver>\` → flip `current` junction → host gracefully stops worker (worker drains: finishes in-flight invocation or journals it, closes WSS with resume token) → host starts new worker. Rollback: if the worker exits abnormally ≥3 times within 5 minutes of a version flip, the host reverts `current` to the previous version directory, marks `<ver>` quarantined in local state, and reports the event to the Gateway on next connect (dashboard alert + automatic rollout-percent freeze is a Gateway-package follow-up). Two version directories retained minimum. Rationale: Section 5.4's self-update duty with the same "old path restorable" iron rule (Section 8) applied at machine granularity.

## (d) Test strategy

1. **Golden-vector compatibility tests (cross-implementation).** The frame codec and signature verifier are ports of proven code; both get byte-exact fixtures: frames captured from the live Node client/add-in pair, and signature envelopes generated by `installer/lib/RevAgent.DistributionIntegrity.psm1` (reusing the negative vectors from `scripts/test-distribution-integrity.ps1:441-449` — unknown key, wrong fingerprint). CI runs these on the Windows runner (`ci.yml` already builds the plugin there).
2. **Live add-in integration** on the existing Windows runner/dev machine with Revit 2022: extend `scripts/test-commandset-live.ps1` conventions with a bridge-driven variant — all 21 commands + `batch_execute` + `get_document_context` invoked through the bridge instead of the Node runtime. This is the primary regression gate proving Section 9's "add-in adapted, not rewritten".
3. **Fault injection is first-class, not incidental** (P3-T13): the bridge's whole reason to exist is flaky-link correctness. Mandatory scenarios: link kill mid-invocation, redelivery after resume, duplicate batch delivery, bridge process kill mid-write (journal recovery), machine sleep/wake, Gateway restart (session resume from store), add-in restart mid-session (Revit closed/reopened).
4. **Self-update drills as automated tests** (P3-T11 acceptance list): every negative path (tamper, downgrade, crash-loop) is a scripted VM test, not a manual checklist — mirroring the house style of `scripts/test-signed-source-free-cd.ps1`.
5. **Installer/uninstaller matrix on VM snapshots**: snapshots provisioned with the real current stack (installer + updater task + dashboard addon + usage-intelligence addon + Codex integration) so the wipe list is tested against reality, including ACL-protected `bootstrap\` removal and the keep-list guard for coordinator/signing hosts. No PowerShell on the Linux CI box — these run on the self-hosted Windows runner or a dedicated test VM, consistent with existing practice.
6. **Static analysis on Linux CI** limited to the .NET build, unit tests, and contract fixtures; anything touching Revit, services, or ACLs runs on Windows.
7. **Pilot = the final test** (Section 8 step 2): a few days of real design work on one workstation exercising reconnects (laptop sleep), self-update (staged manifest), and the busy/serial semantics before the fleet cutover.

## (e) Risks specific to this package

| # | Risk | Mitigation |
|---|---|---|
| R1 | **RevitMCPSDK is external and version-pinned per Revit release** (`revAgentPlugin.csproj:46`); any add-in change that would need SDK type changes stalls. | P-ADDIN designs deliberately avoid SDK type changes (new commands use existing `ExternalEventCommandBase` pattern; `get_document_context` bypasses registry dispatch like `mcp_status`). Flag early if `batch_execute` needs anything from the SDK beyond `IRevitCommand`. |
| R2 | **Add-in DLL swap blocked by running Revit** turns self-update of the add-in into a long-tail deferral (users who never close Revit). | Deferred-apply state is reported to the Gateway and surfaced on the dashboard (P-UPD-3); runbook includes an admin nudge policy. Same behavior as today's updater, so no regression — but now it's observable. |
| R3 | **SQLite native library in single-file publish** (e_sqlite3 extraction) can misbehave under aggressive AV/whitelisting on customer fleets. | Pin `SQLitePCLRaw.bundle_e_sqlite3`, extract to the ProgramData state root (not %TEMP%), verify in the installer's end-to-end check; fallback design (append-only journal file) documented but not built unless needed. |
| R4 | **Wipe-list collateral damage**: the uninstaller removes ACL-protected trees and per-user Codex files; a bug destroys the coordinator's `revAgentOps` evidence or the CD runner's signing keys — the latter would kill O9 signing permanently. | Hard keep-list guard with host detection + explicit `-Force` (P3-T10 acceptance); signing-key tree additionally backed up before cutover night (runbook step); wipe never touches `C:\ProgramData\DPE\revAgentReleaseSigning` even with `-Force`. |
| R5 | **Corporate proxy/TLS interception breaks WSS** on proxy-configured machines (E4 shows machine-wide `HTTPS_PROXY` is a real fleet condition). | Bridge honors system/env proxy for WSS and supports custom CA trust via machine store; `doctor` verb diagnoses proxy/TLS failures explicitly; tested in P3-T4 with a MITM proxy in the harness. |
| R6 | **Orphaned local clients after cutover**: anything still targeting TCP 8080 (dev scripts, stale Codex config on unmanaged machines) collides with the bridge's exclusive-client assumption. | Loopback bind (P-ADDIN-1) plus the retained `mcp_status` preflight and intake lock (P-ADDIN-4) make a rogue client visible and harmless; wipe-report scan flags leftover Codex registrations. |
| R7 | **O1 slippage serializes the critical path** (T4/T5/T7 blocked). | Start O1-independent tasks first (T1/T2/T3/T6/T9/T10/T12); build the O1 conformance stub jointly with the Gateway package so bridge and gateway develop against the same executable spec. |
| R8 | **Crash-loop rollback masks a bad-but-not-crashing release** (hangs, silent failures). | Host also monitors worker liveness via a local health ping (heartbeat to Gateway acknowledged); "connected within N minutes of start" counts toward the rollback criterion, not just process exit. |
| R9 | **Enrollment tokens leak on cutover night** (tokens in scripts/consoles across ~12 machines). | Single-use + short TTL (P-ENROLL-1); Gateway audit-logs every enrollment (Section 5.1.4); runbook revokes unused tokens at end of window. |
