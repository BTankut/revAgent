## 1. Runtime anatomy — `installer/runtime-mcp-server/`

**Package identity & footprint**
- `package.json:2-11` — name `revagent-runtime` v1.0.0, private, ESM (`"type":"module"`), bin aliases `revagent-runtime` and `revit-mcp` → `build/index.js`.
- Source: 75 TS files, 26,230 lines under `src/` (`src/index.ts`, `src/tools/` 46 files, `src/spatial/` 15 files, `src/utils/` 13 files, `src/database/` 2 files).
- Dependencies (`package.json:75-84`): `@modelcontextprotocol/sdk ^1.29.0`, `zod ^3.24.2`, `better-sqlite3 12.9.0` (native, exact-pinned), `ajv ^8.20.0` + `ajv-formats`, `@e965/xlsx`, `csv-parse`, `ws ^8.20.1`. **`ws` is declared but never imported anywhere in src — dead dependency, drop it.** Security `overrides` block at `package.json:85-91`.
- tsconfig: ES2022 / NodeNext / strict, `src` → `build` (`tsconfig.json:2-15`).

**Entry point & transport**
- `src/index.ts:8-28`: single entry. Creates `McpServer({name:"revAgent", version:"1.0.0"})`, `registerTools(server)`, `initializeSpatialStore()`, then `StdioServerTransport` + `server.connect(transport)` (`index.ts:19-20`). Transport is **stdio only**; the SDK version (^1.29.0) already ships `StreamableHTTPServerTransport`, so the literal transport swap is a one-file change — but see §6: under D4 the tools stop terminating at MCP directly.
- Secondary CLI mode: `node build/index.js spatial-store …` runs a local spatial-store maintenance CLI (`index.ts:9-11`, `src/spatial/spatialStoreCli.ts`), referenced by operator instructions in `installer/codex-user/AGENTS.md:83-88` with a hardcoded `%ProgramData%` path.

**Tool registration — code-defined, no schema files**
- `src/tools/register.ts:39-77`: 35 tools registered imperatively via `server.tool(name, description, zodShape, handler)` (interface `src/tools/types.d.ts:10-22`); every registration is wrapped by `wrapServerWithTelemetry` (`src/utils/telemetry.ts:1820-1935`) which intercepts `tool()` and wraps handlers with telemetry + live-activity recording. Tool input schemas are inline zod objects (e.g. `src/tools/export_revit_view_image.ts:65-82`). The only JSON-schema files are the spatial page/snapshot contracts (`schemas/spatial/v0.1|v0.2|v0.3/*.schema.json`, validated with ajv in `src/spatial/spatialPageSchema.ts`).
- Tool inventory (35): status/discovery `list_revit_instances`, `get_revit_mcp_status`; dynamic code `send_code_to_revit`, `send_code_to_revit_safe`; context `get_revit_session_context`, `get_active_view_context`, `get_ui_state`, `list_open_views`; navigation/view `activate_view`, `close_view`, `clear_selection`, `delete_review_view`, `open_existing_plan_for_element_level`, `focus_elements`, `section_box_elements`, `create_3d_view_for_elements`, `show_element_in_plan_and_3d`, `smart_focus_elements`; inspection `find_elements`, `inspect_elements`, `inspect_levels`, `inspect_sheet_text`, `inspect_schedules`, `inspect_parameter_schema`, `count_annotations`; export `export_revit_view_image`, `export_revit_coordination_image`; writes `set_element_parameter`, `set_schedule_cells`, `set_schedule_cells_by_text`; reconciliation `reconcile_schedule_excel`; spatial `capture_spatial_snapshot`, `query_spatial_context`, `compare_spatial_snapshots`, `summarize_spatial_state`. Most tools generate C# code strings executed by the add-in (`csharpString`/`csharpStringArray`/`csharpIntArray` codegen helpers, `src/utils/revitToolHelpers.ts:539-560`).
- A proto policy-class layer already exists (input to D12): write-pattern regex guards `src/tools/send_code_to_revit_safe_guards.ts:1-27` (21 named patterns); `send_code_to_revit_safe` rejects `writeCommit` intent and `transactionMode:"auto"` (`src/tools/send_code_to_revit_safe.ts:33-52`); raw `send_code_to_revit` is the explicit-confirmation path.

**TCP client to the add-in**
- `src/utils/SocketClient.ts` (`RevitClientConnection`):
  - Framing: 4-byte big-endian length prefix + UTF-8 JSON-RPC 2.0 payload (`writeCommand` :396-406; decode :185-211). Max frame 32 MiB (`MAX_RESPONSE_BYTES`, :4). Auto-detecting **legacy raw-JSON fallback** (brace-balance scanner :130-183; heuristics :97-111; runtime downgrade to legacy on framing errors :316-339; env override `REVAGENT_FRAMING`/`REVIT_MCP_FRAMING` :43).
  - Correlation: request `id` = `Date.now() + random` (:274-276); `responseCallbacks: Map<string,cb>` (:41); unmatched **error** responses are delivered to the single pending callback, or broadcast to all pending if >1 (:223-238) — loose correlation that O1 should tighten.
  - Timeouts: default command timeout **120 s** (:378-384); busy-preflight `mcp_status` call before every non-status command with 3 s cap (:278-304, :287) — 2 TCP round-trips per tool call today.
- Connection lifecycle: `src/utils/ConnectionManager.ts:323-366` `withRevitConnection` — a **new socket per tool invocation**, 5 s connect timeout (:354), `disconnect()` in `finally` (:363). There is **no persistent connection and no reconnect/backoff logic anywhere** — the bridge (O1) must add both.
- Multi-instance targeting: default `localhost:8080` via `REVAGENT_HOST/PORT` (legacy `REVIT_MCP_*`, `REVIT_*`) (`ConnectionManager.ts:35-36`); target selection by port / `host:port` / registered instance name (:214-243); discovery via port scan 8080-8085 (:263-265) plus instance-registry JSON files in `os.tmpdir()` (`revAgent-instances.json`, `revit-mcp-instances.json`, :37-42) written by the add-in side.
- Cross-process serialization: mkdir-based lock dirs `os.tmpdir()/revit-mcp-command-locks/<host>-<port>.lock`, 8 s wait, 10 min stale reap, 250 ms poll (`ConnectionManager.ts:43-46, 276-321`) — this is the current "serial per Revit session" enforcement, filesystem-based and same-machine-only.

**Session/state held in the runtime process**
- Module-level singletons everywhere — the runtime assumes **one user, one machine, one Codex session per process**: telemetry session UUID + sequence counter (`telemetry.ts:55-56, 145`), in-memory live task maps (`telemetry.ts:146-150`), spatial-store singleton (`src/spatial/spatialStoreManager.ts:26-34`), framing-mode per connection. Zero multi-tenancy.
- Durable state: spatial SQLite store at `%LOCALAPPDATA%\revAgent\spatial\spatial.db` (better-sqlite3 + R-tree; `src/spatial/spatialStore.ts:772-787`), with a fail-closed local-disk policy: UNC/URL rejection (:690-697), Windows drive-type probe via `spawnSync("powershell.exe")` (:699-732, skipped when `process.platform !== "win32"` :746), managed-package-path rejection (:762-768). Graceful capability degradation when the native binding is missing (`spatialStoreManager.ts:48-50, 88-97`).
- Dead code: `src/database/db.ts` + `service.ts` (legacy `revit-data.db` SQLite at package root, `db.ts:8`) has **no importers** — delete, do not migrate.

**Config/env consumption**
- `src/utils/env.ts:1-9` alias reader; alias pairs `REVAGENT_*` ⇄ legacy `REVIT_MCP_*` for HOST/PORT/PORTS/TARGET/FRAMING/INSTANCE_REGISTRY (covered by `scripts/env-alias.test.mjs`).
- Telemetry envs: `REVAGENT_TELEMETRY_DISABLED/_LOCAL_ONLY/_ROOT/_TEXT_CHARS/_CODE_CHARS/_CONTEXT_ELEMENTS`, `REVAGENT_REPORTS_ROOT`, live-status envs `REVAGENT_LIVE_STATUS_*` (`telemetry.ts:152-212, 1194-1240`).
- Spatial envs: `REVAGENT_SPATIAL_DB_PATH`, `REVAGENT_SPATIAL_RETENTION_DAYS/_MIN_COMPLETE_SNAPSHOTS/_RETENTION_DISABLED` (`spatialStore.ts:32-34, 776`).
- Installer-written config files read at runtime: `updater/updater-config.json` and `updater/installed.json` discovered under install root and `%ProgramData%\DPE\revAgent|RevitMCP` (`src/utils/runtimeIdentity.ts:46-79`) — supplies `reportsRoot` (NAS telemetry target) and runtime version/build hash.

**Logging/telemetry**
- Console: `console.error` only (stdio-safe) (`index.ts:22-23`, `register.ts:76`).
- Structured telemetry: every MCP tool call and every Revit command emits NDJSON events (`revagent.telemetry.v1`) to local `%ProgramData%\DPE\revAgent\state\telemetry\events\<date>.ndjson` **and** to a NAS `reportsRoot` per-year/month/day/machine/session file (`telemetry.ts:1211-1231, 1754-1762`); serialized queued appends (`src/utils/telemetryWriters.ts:21-37`).
- Live status: heartbeat JSON snapshot every 5 s per machine (`telemetry.ts:1709-1726, 1513-1522`) with cross-session merge logic (:1490-1511) — this is what the dashboard/usage-intelligence addons consume today (O11 relevance: the event vocabulary here — params/response summarization :378-503, spatial privacy boundary :218-307/568-676, element/document/view context extraction :1033-1184, and a regex **discipline-inference** function :924-960 — is the de-facto draft of the O7 event schema, and the discipline inference is a proto planner/router signal for §5.2 stage 2).

## 2. How the loop is driven TODAY

- **The agentic loop is 100% external.** There is zero LLM/prompt/loop code in the runtime (no LLM API reference anywhere under `installer/runtime-mcp-server/`). The MCP client and loop driver is the unified ChatGPT/Codex desktop app (Codex CLI), configured by the installer:
  - `installer/lib/RevAgent.CodexRegistration.psm1:3394-3402` writes TOML blocks; `:3566-3567` (and `:310-311`) register `[mcp_servers.revAgent]` → `command = <attested node.exe>`, `args = [<install>\package\installer\runtime-mcp-server\build\index.js]`, and `[mcp_servers.revAgent-api-docs]` → docs server, into `CODEX_HOME/config.toml` (`:3525`), with atomic tmp/backup/rollback writes (`:3548-3710`) and post-write verification via `codex mcp get … --json` (`:4181-4198`). Legacy names `revit-mcp`/`revit-api-docs` are migrated out (`:306, :3562-3565`).
  - Node discovery is locked to canonical `C:\Program Files\nodejs\node.exe` with Authenticode/hash/hardlink attestation and guarded launch (`:3182-3276, 4218-4260`).
- **AGENTS.md / SKILL.md install locations and readers:**
  - Deployed production copies live in `installer/codex-user/` (AGENTS.md 135 lines, SKILL.md 170 lines); the repo-root `AGENTS.md` (402 lines) / `SKILL.md` (918 lines) are the dev-workstation instruction set (fallback source only if `installer/codex-user/SKILL.md` is absent — `installer/install-self-contained.ps1:617-620`).
  - AGENTS.md → `CODEX_HOME\AGENTS.md` as a managed file (marker `AGENTS.md.revagent-managed.json`, atomic replace) (`RevAgent.CodexRegistration.psm1:334, 4033-4075`); machine copy at `<InstallRoot>\codex\AGENTS.md` (`install-self-contained.ps1:677`).
  - SKILL.md → canonical `%USERPROFILE%\.agents\skills\revAgent` (legacy `.codex\skills\revAgent`, `.codex\skills\revit-mcp`) (`RevAgent.CodexRegistration.psm1:3852-3864`); machine copy under `<InstallRoot>\codex\skills\revAgent` (`install-self-contained.ps1:670-676`). Both read only by the Codex app.
- **Loop behavior is encoded as prose, not code** — these rules become orchestration-engine code in the Gateway: mandatory `get_revit_mcp_status` poll before every non-status tool + no parallel tool calls (`installer/codex-user/AGENTS.md:102-107` — today's serial-per-session enforcement at the prompt layer, duplicating the tmpdir lock at the process layer); mandatory tool-routing table (`:51-100`); visual-QA sequence (`:113-127`); memory-vs-SKILL precedence (`:26-28`).
- `config/dynamic-tool-promotion-registry.json` + `-rules.json`: consumed only by the usage-intelligence summarizer (`addons/usage-intelligence/scripts/summarize-usage-intelligence.ps1`), not by the runtime — offline flagging of repeated `send_code_to_revit` hashes / write patterns / manual transactions as candidates for promotion to native tools (schema: states candidate/promoted/watch/rejected; `repeatThreshold: 2`). This is a Tool-Registry-adjacent concept that should live in the Gateway registry going forward.

It is also a low-risk **pilot candidate for the first internal MCP server registration path** that the CSI module will later use.

## 5. Migration-relevant couplings (each with file:line)

Same-machine / Windows assumptions that matter when the runtime moves to a Linux Gateway container:

1. `src/utils/ConnectionManager.ts:35-36` — default Revit target `localhost:8080`; the whole TCP client presumes the add-in is on the same host. Becomes the bridge's southbound config; in the Gateway, tool dispatch must go to a bridge session instead.
2. `src/utils/ConnectionManager.ts:37-43` — instance registry (`os.tmpdir()/revAgent-instances.json`) and lock root (`os.tmpdir()/revit-mcp-command-locks`) are same-machine cross-process IPC; meaningless in a container. Replace with Gateway per-session serial queues (§5.2 rule 1) + bridge session registration.
3. `src/utils/ConnectionManager.ts:263-265` — localhost port scan 8080-8085 for multi-Revit discovery; replaced by bridge session registration of `(user, machine, open documents)`.
4. `src/utils/runtimeIdentity.ts:43` — `C:\ProgramData` fallback; `:46-79` updater-config/installed.json discovery under `%ProgramData%\DPE\…` — NAS-updater coupling, dies with the NAS retirement.
5. `src/utils/telemetry.ts:1249, 1452, 1744` — `COMPUTERNAME` (and `USERNAME` at `:1453, 1745`) identity; replace with Gateway session/tenant identity.
6. `src/utils/telemetry.ts:1199-1200, 1223-1229` — remote telemetry writes to NAS `reportsRoot` (SMB path from updater-config); entire file-drop transport is replaced by the O7 event stream.
7. `src/spatial/spatialStore.ts:711-722` — `spawnSync("powershell.exe")` drive-type probe (Linux: skipped via the `win32` guard at `:746`, so not a crash, but the fail-closed policy intent must be re-expressed for container volumes); `:780-783` default DB path from `LOCALAPPDATA` degrades to `~/AppData/Local/...` on Linux — re-home to the Gateway data layer, per-tenant.
8. `src/tools/export_revit_view_image.ts:45-47, 86` and `src/tools/export_revit_coordination_image.ts:49` — **the biggest file-exchange coupling**: output dir defaults to the *runtime's* `os.tmpdir()`, but the file is written by *Revit* (the generated C# runs `Document.ExportImage` on the workstation) and the local path is returned to the model/user. Works only because runtime and Revit share a disk. In the target: image lands on the workstation → bridge must upload bytes → object storage `result_ref` (§5.2 stage 5) → the tool returns a ref, not a path.
9. `src/tools/reconcile_excel_ingestion.ts:642, 736, 996` — `XLSX.readFile` / `fs.readFile` / `fs.stat` on a user-supplied local path (`excel.path`, example `C:\path\items.xlsx` at `src/tools/reconcile_schedule_excel.ts:154`): assumes the user's Excel file is on the runtime machine. Needs an upload channel (web client) or a bridge file-fetch primitive in O1.
10. `installer/revit-api-docs-mcp/src/utils/docIndex.ts:127-135, 191-225` — `C:\Program Files\Autodesk` root, `C:\ProgramData` cache, `spawn("powershell")` index builder (hard break on Linux; see §3 fix).
11. `src/utils/runtimeIdentity.ts:86-88` — local telemetry root under `%ProgramData%`.
12. `installer/codex-user/AGENTS.md:83-88` — instruction layer hardcodes `%ProgramData%\DPE\revAgent\package\installer\runtime-mcp-server\build\index.js` for the spatial-store CLI; must be re-authored when AGENTS/SKILL move into the Tool Registry (§9 of the architecture doc).
13. `src/utils/SocketClient.ts:278-304` — per-command `mcp_status` busy preflight duplicates state the bridge will hold; fold into bridge session state in O1. Loose error correlation at `:223-238` should become strict id-matching in the O1 protocol.
14. Process-model assumption: one stdio process per Codex session; all singletons (telemetry session id `telemetry.ts:55`, live task maps `:146-150`, spatial store `spatialStoreManager.ts:26`) must become per-session/per-tenant scoped objects in the Gateway. **There is no tenancy concept anywhere in the runtime.**

Non-issues verified: `csharpString` codegen is platform-neutral (`revitToolHelpers.ts:539-560`); LF newlines enforced (`tsconfig.json:13`); no registry/win32 API/node-gyp usage besides better-sqlite3; spatial store's non-Windows path checks pass on Linux.

## 6. Reusable in the Gateway vs rewrite candidates

**REUSABLE (transplant with mechanical changes)**
- All 35 tool modules' core logic: zod input schemas, C# codegen templates, guard logic, and result-shaping — these become registry-declared tools whose executor binding is "bridge". The zod schemas are the seed data for the Tool Registry (D5 capability index + deferred full schemas); tool names/descriptions need the discipline-prefix rename pass (§5.3), e.g. `find_elements` → `mech.query.find_elements`-style.
- Result/contract layer, unchanged: `runtimeResult.ts` (completed/guarded/failed contract), `broadScanResult.ts`, `responseMode.ts` (compact/full/debug + row compaction), `revitToolHelpers.ts` normalization (`normalizeSuccessCasing`, `normalizeRevitExecutionResponse`, `compactMcpStatusPayload`, `trimPlanCandidatesInPayload` — this is exactly §5.2 stage-5 "result hygiene" already implemented), `searchPolicy.ts` (budget presets fast/balanced/deep + risk policy — feeds D12 `auto`/`confirm` classification and the guardrail engine).
- `send_code_to_revit_safe_guards.ts:1-27` write-pattern classifier — direct seed for the D12 policy-class enforcement (`confirm` detector) in the orchestration engine.
- The **entire spatial subsystem** (~2,884-line store + capture/query/diff/summary + versioned JSON schemas + golden-file tests): pure compute over SQLite; re-home DB per-tenant into the Gateway data layer, drop the PowerShell drive probe, keep everything else.
- The reconciliation engine (`reconcile_*` modules): pure compute; swap the file source for upload/`result_ref` input.
- `SocketClient.ts` — becomes the **bridge's** southbound half essentially unchanged (D4 keeps add-in↔bridge TCP framing); it is the reference implementation of the proven framing.
- Telemetry *summarization* functions (`summarizeTelemetryParams/Response`, spatial privacy boundary, `extractProductionContext` incl. discipline inference `telemetry.ts:924-960`) — the starting vocabulary for the O7 event schema; discipline inference doubles as planner/router training signal (§5.2 stage 2).
- Test suites (contract `.mjs` tests + golden fixtures) — port to Gateway CI as-is.
- MCP SDK usage: `@modelcontextprotocol/sdk ^1.29.0` already supports Streamable HTTP; the north-boundary remote MCP server can be built on the same SDK.

**REWRITE / RETIRE**
- `ConnectionManager.ts` — entire file: tmpdir locks, port scan, per-call connect/disconnect, lock stale-reaping → replaced by Gateway session routing, per-session serial dispatch queues, and the O1 bridge protocol (its lock/stale semantics inform the idempotency-journal design; the code dies).
- `index.ts` bootstrap — trivially rewritten for the Gateway process model (registry-driven tool loading instead of static `register.ts`; static registration remains fine for Phase 1).
- Telemetry transport: `telemetryWriters.ts`, `resolveTelemetryTargets`, live-status heartbeat/merge (`telemetry.ts:1441-1522, 1709-1726`) — file/NAS drops die; events go to Postgres/event stream; live status becomes Gateway session state read by the dashboard (O11 metric-parity check should be run against the event fields enumerated in §1 above).
- `runtimeIdentity.ts` updater/installed.json discovery — dies with NAS.
- `src/database/{db,service}.ts` — dead code, delete.
- `ws` dependency — unused, remove.
- Per-command `mcp_status` preflight (`SocketClient.ts:278-304`) — replaced by bridge-held busy state + Gateway queueing; eliminates 1 round-trip per tool call.
- Instruction-layer workstation paths (`installer/codex-user/AGENTS.md:83-88`) — re-authored when AGENTS/SKILL are served from the Tool Registry.
- `revit-api-docs-mcp` index builder — moves to CI (Windows step); query server code reused as a gateway-internal tool module (§3).

**Net assessment:** the runtime is a well-tested tool library wearing a thin stdio coat. ~80% by volume (tools, spatial, reconciliation, contracts, tests) transplants; the ~20% that dies is precisely the same-machine plumbing (connection management, tmpdir locking, file telemetry, updater identity) that the Gateway/Bridge split replaces by design. The in-house orchestration engine inherits no loop code from this repo — today's loop is entirely the Codex desktop app plus prose rules in AGENTS/SKILL, which is the cleanest possible starting point for D9.
