## 4) Signing infrastructure available for O9 (bridge self-update)

**Core module:** `installer/lib/RevAgent.DistributionIntegrity.psm1` — byte-pinned across the updater privilege boundary (lines 1-2).
- Constants: canonicalization `RFC8785-JCS-SHA256-v1`, algorithm `RS256` (lines 5-6).
- **Sign:** `New-RevitMcpDetachedJsonSignature` (lines 267-325). Envelope fields: `{schemaVersion:1, app, signedObject, algorithm:"RS256", keyId, publicKeyFingerprint, canonicalization, contentSha256, createdAtUtc, signature}` (lines 299-310). `contentSha256` = SHA-256 of RFC8785-canonical JSON of the signed document (lines 202-228, 307); signature = RSA PKCS#1 v1.5 / SHA-256 (`RSACryptoServiceProvider.SignData(payload,"SHA256")`) over the canonical JSON of the envelope with `signature=""` (lines 312-317). `signedObject` is an allowlist pinned to exactly `channel | release-manifest | license-seat` (lines 290-296).
- **Verify:** `Test-RevitMcpDetachedJsonSignature` (lines 838-912; content-hash check 855-865, key lookup by keyId 867-869, fingerprint pin 877-884, `VerifyData` 894-898) and file wrapper `Test-RevitMcpDetachedJsonSignatureFile` (lines 914+). Fingerprint = SHA-256 of the whitespace-stripped **RSA public key XML string** (lines 230-241) — a .NET-specific detail.
- **Key handling:** private key is an RSA XML file on the CD runner only: `C:\ProgramData\DPE\revAgentReleaseSigning\private\revagent-prod-rsa-2026q3-private.xml`; public single-key trust doc `...\public\release-trusted-keys.json`; key id `revagent-prod-rsa-2026q3`; fingerprint `32F8BD0B4E905BB58606FB226459C09A6AE2CFC10A4E94203566FE4ADD7BBE33` (docs/DEVELOPER_RUNBOOK.md:1000-1011; pinned in code at scripts/invoke-signed-source-free-cd.ps1:41-42, 278-295 and scripts/publish-signed-source-free-release-to-nas.ps1:1529-1532). Production accepts exactly one key; no multi-key overlap; rotation is a 6-step coordinated code+prestage procedure (docs/DEVELOPER_RUNBOOK.md:1013-1036). Public keys ship to workstations inside release `tools\config\release-trusted-keys.json` (docs/DEVELOPER_RUNBOOK.md:974-976).

**Reuse plan for the O9 bridge-update manifest:**
1. Reuse the envelope format verbatim; add one new `signedObject` value (e.g. `bridge-update-manifest`) to the allowlists at RevAgent.DistributionIntegrity.psm1:291 and :844 (verification default). Gateway serves `manifest.json` + `manifest.sig.json`; bridge verifies with the pinned single-key document before applying.
2. Signing can keep happening in CD on the `revagent-cd` runner with the existing key/environment (`revagent-release-signing`), so no new key custody problem; the Gateway only *distributes* signed artifacts (matches the existing model where NAS is "signed transport, not trust" — docs/DEVELOPER_RUNBOOK.md:1078-1089).
3. **Porting caveats (bridge will not be PowerShell):** a Node/Go/.NET bridge verifier must reimplement (a) RFC8785/JCS canonical JSON, (b) the envelope-with-empty-signature payload construction, (c) RSA PKCS#1v1.5-SHA256 verify, and (d) either parse .NET RSA XML public keys or the plan should publish the same key additionally as PEM/JWK (fingerprint definition must then be restated, since today it hashes the XML string — DistributionIntegrity.psm1:238-240). Cheapest path: keep XML+fingerprint semantics and port the ~30 lines of XML-modulus/exponent parsing; cleanest path: dual-publish PEM at the next key rotation window.
4. Carry over `releaseSequence` monotonicity + `minimumAcceptedReleaseSequence` from the channel schema for anti-downgrade in the bridge journal (mirrors `highestAcceptedReleaseSequence` behavior, docs/DEVELOPER_RUNBOOK.md:1301-1307), and keep the pilot-cohort concept (`PilotAllowedMachineNames`, publish-nas-release.ps1:1293-1301) as the staged-rollout primitive O9 asks for.

## 5) Rollback reality for D11 ("restore old stack from NAS")

Facts that constrain the rollback criterion:

1. **The exit-84 prestage constraint makes NAS restore non-self-service on any machine whose protected bootstrap was wiped.** Current production behavior: if `C:\ProgramData\DPE\revAgent\bootstrap` is missing or fails verification, every NAS Refresh path that would elevate returns **exit 84 before UAC**, and direct `-ElevatedApply` is disabled (CHANGELOG.md:28-39; installer/INSTALLATION.md:40-49; docs/BOOTSTRAP_PRESTAGE.md:14-19, 30-37). Recovery is the supervised two-shell manual prestage: a trusted coordinator shell on a clean merged checkout produces signed evidence, then a fresh **elevated shell run at the machine** stages the bootstrap with hand-carried literals (docs/BOOTSTRAP_PRESTAGE.md:51-120; scripts/install-revagent-local-bootstrap.ps1:468-551). That is an admin-at-keyboard procedure **per machine** — across ~12 machines this is hours of supervised work, not "run the NAS script".
2. **The scheduled task cannot restore anything.** `revAgent Auto Update` is audit-only, with no install/mutate authority (installer/INSTALLATION.md:92-93; docs/DEVELOPER_RUNBOOK.md:84-85 area, 1427-1430). Restore requires an interactive protected-GUI `Install/Repair` run per machine.
3. **Revit-close policy applies to restore.** Re-installing add-in/command DLLs requires Revit closed on each machine (installer/INSTALLATION.md:163-165; docs/DEVELOPER_RUNBOOK.md:1578-1597) — rollback night has the same scheduling constraint as cutover night.
4. **Sequence guards do not block same-version restore, with one trap.** Workstations reject only *older* signed sequences than their persisted `highestAcceptedReleaseSequence` (docs/DEVELOPER_RUNBOOK.md:1263-1265, 1301-1307); re-applying the frozen stable (equal sequence) is a repair, not a rollback. NAS-side, republishing lower/equal sequences needs `allow_rollback=true` / `-AllowRollback`, never bypassing signature validation (signed-source-free-cd.yml:43-47, 545-547; scripts/publish-signed-source-free-release-to-nas.ps1:2173-2174). Trap: if the bridge era ever publishes a *higher-sequence signed release* that workstations accept, going back requires the manual local flag `-AllowSignedReleaseRollback` per machine (docs/DEVELOPER_RUNBOOK.md:1304-1307). Plan rule: during the 2-week insurance window, publish nothing new to the frozen NAS channel.
5. **Codex re-registration is part of restore.** Rolling back also means re-running the unelevated user phase to restore `[mcp_servers.*]` entries, AGENTS.md, and skill (§1.3) — the Store-bound Codex attestation must still pass, i.e., the ChatGPT desktop app must still be installed and current on every machine (docs/DEVELOPER_RUNBOOK.md:1470-1503).

**Consequence for the plan (honest D11 rollback criterion):** "restore old stack from NAS once" is only cheap if cutover night **disables rather than deletes** the rollback-critical set for the 2-week window. Recommended two-stage wipe: (Stage A, cutover night) remove/neutralize only what conflicts with the bridge — the two Codex `[mcp_servers.*]` entries, managed AGENTS/skill files, the `revAgent Auto Update` task + Startup fallback + desktop launcher — while leaving `C:\ProgramData\DPE\revAgent\{bootstrap, updater, package, runtime, state}` and the frozen NAS tree intact (the old runtime is inert once its Codex registration is gone; Codex was the only thing that spawned it). Rollback then = re-run the protected GUI user phase + re-register the task: minutes per machine, no elevation beyond the still-verified bootstrap, exit-84 never triggers. (Stage B, after NAS retirement) run the full §1 wipe list including bootstrap/prestage/updater and legacy roots. If the plan instead insists on a full Stage-A wipe, the rollback criterion must explicitly budget the supervised per-machine prestage procedure (item 1) and state that rollback is a multi-hour, admin-supervised operation — otherwise D11's "restore once" promise is not real.

**NAS freeze mechanics:** freezing = stop all publishes; the signed `channels\stable.json` + `releases\<version>` + `tools\` tree stays valid as-is because workstation trust is anchored in the local bootstrap's pinned keys, not in NAS ACLs (docs/DEVELOPER_RUNBOOK.md:1078-1089). Archive = copy the release root; nothing in the channel JSON is machine-specific (relative paths, docs/DEVELOPER_RUNBOOK.md:1159-1161).
