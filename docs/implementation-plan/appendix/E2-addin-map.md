# TASK E2 — C# Revit Add-in & TCP Boundary Map

Repo: /home/user/revAgent. Two projects in src/revit-plugin/revAgentPlugin.sln: `revAgentPlugin` (host: socket server, dispatch, config, UI) and `revAgentCommandSet` (the 21 command implementations, loaded by reflection). Shared base types (`IRevitCommand`, `ICommandRegistry`, `ExternalEventCommandBase`, `IWaitableExternalEventHandler`, JSON-RPC models) come from the external NuGet `RevitMCPSDK` (version-matched per Revit release, `RevitMCPSDK:$(RevitVersion).*` — src/revit-plugin/revAgentPlugin/revAgentPlugin.csproj:46) — NOT in this repo; any protocol change touching those types must either wrap or replace the SDK.

## 1) TCP server, framing, threading

**Server class:** `SocketService` (singleton) — src/revit-plugin/revAgentPlugin/Core/SocketService.cs.

- **Framing:** 4-byte big-endian length prefix + UTF-8 JSON payload. Parse: SocketService.cs:336-367 (`ReadNetworkInt32` at 343, impl 446-452); write mirrors it: `WriteResponse` SocketService.cs:454-468. Client side (Node runtime): `writeCommand` header `writeUInt32BE` — installer/runtime-mcp-server/src/utils/SocketClient.ts:396-406; response reassembly SocketClient.ts:185-211.
- **Dual-framing back-compat:** per-connection auto-detection between `LengthPrefixed` and `LegacyJson` (raw unframed JSON object) — `DetectMessageFraming` SocketService.cs:416-439; legacy path 370-383 (brace-balancing extraction on client: SocketClient.ts:130-183). Client defaults to length-prefixed (`REVAGENT_FRAMING`/`REVIT_MCP_FRAMING` env override, SocketClient.ts:43) and falls back to legacy once on framing-shaped errors (SocketClient.ts:316-339). O1 note: the legacy path is a cutover-era compatibility shim; the Bridge can standardize on length-prefixed only.
- **The 8192-byte fix:** `SocketReadBufferBytes = 8192` is now only the per-read chunk size (SocketService.cs:19); reads accumulate into a `MemoryStream pending` and messages are re-framed from the buffer (`HandleClientCommunication` SocketService.cs:243-313, loop 292-297), removing the old "one 8 KB read = one message" limit. Message size cap: 16 MiB default, 128 MiB absolute, env `REVAGENT_MAX_MESSAGE_BYTES`/`REVIT_MCP_MAX_MESSAGE_BYTES` (SocketService.cs:20-21, 67-76); oversize → error response + connection abort (281-290, 344-352). Client cap 32 MiB (SocketClient.ts:4, 74-78).
- **Message format:** JSON-RPC 2.0. Request `{jsonrpc:"2.0", method, params, id}` (SocketClient.ts:349-354). **Correlation id** = JSON-RPC `id`, generated client-side as `Date.now()+random` string (SocketClient.ts:274-276), echoed in responses, matched via `responseCallbacks` map (SocketClient.ts:213-239). Success responses embed the result with `resultContractVersion: 2` stamped and camelCase serialization (`BridgeResultContract.CreateResultPayload` — src/revit-plugin/revAgentPlugin/Core/BridgeResultContract.cs:10, 25-40). Error responses `{id, error:{code,message,data}}` with SDK `JsonRPCErrorCodes` (ParseError/InvalidRequest/MethodNotFound/InternalError — SocketService.cs:515-533, 611, 627-644). Side-channel display params recognized in `params`: `taskName|displayName|operationName`, `wrapperAction`, `logicalToolName|toolName`, `parentTaskName`, `parentTaskId`, `suppressTaskStatusWindow` (SocketService.cs:539-547) — these exist for the in-Revit task-status window and are a de-facto envelope extension O1 should formalize.
- **Port/binding:** `TcpListener(IPAddress.Any, port)` — SocketService.cs:157 — i.e. **bound on all interfaces, no auth**. Default port 8080 (SocketService.cs:44; ServiceSettings.cs:20); resolution order env `REVAGENT_PLUGIN_PORT|REVAGENT_PORT|REVIT_MCP_PLUGIN_PORT|REVIT_MCP_PORT` → commandRegistry.json `settings.port` → 8080 (SocketService.cs:86-109). On `AddressAlreadyInUse` auto-increments up to +20 (SocketService.cs:149-185) — supports multiple concurrent Revit sessions per machine. Runtime client defaults host `localhost`, port 8080 (ConnectionManager.ts:35-36) and scans candidates [8080..8085] plus an optional instance-registry file `%TMP%/revAgent-instances.json` (ConnectionManager.ts:37-42, 245-274; nothing in the repo writes that file — read-only facility).
- **Single vs multi client:** multi-client TCP: dedicated listener thread accepts any number of clients, one background thread per connection (SocketService.cs:162-166, 218-241, 224-230). No client identity. Within a connection, requests are processed strictly sequentially (response written before next frame parsed).
- **Marshaling onto the Revit API thread:** ExternalEvent, not Idling. Each command subclasses SDK `ExternalEventCommandBase` holding its own `IExternalEventHandler`+`IWaitableExternalEventHandler`; `Execute` runs on the socket thread, sets handler params, then `RaiseAndWaitForCompletion(timeoutMs)` raises the ExternalEvent and blocks on a `ManualResetEvent` until the handler (running in Revit API context on the UI thread) signals (pattern: ExecuteCodeCommand.cs:38-48, GetSelectedElementsCommand.cs:36-46; handler `Execute(UIApplication)` + `_resetEvent` ExecuteCodeEventHandler.cs:43-101). ExternalEvents are cached per handler key by `ExternalEventManager.GetOrCreateEvent` (src/revit-plugin/revAgentPlugin/Core/ExternalEventManager.cs:45-80). Per-command wait timeouts: e.g. 15 s (GetSelectedElementsCommand.cs:39), 60 s (ExecuteCodeCommand.cs:41); client-side timeout default 120 s (SocketClient.ts:378).
- **Serial-execution guarantees:** Revit itself serializes all ExternalEvent handlers on the UI thread — actual Revit API work is serial per session by construction. However the add-in does NOT serialize request intake: concurrent clients can invoke the same singleton command instance and race handler parameter state (only some commands defend, e.g. `GetSelectedElementsCommand._executionLock` GetSelectedElementsCommand.cs:16, 28; `ExecuteCodeCommand` has no lock). Effective serialization today is enforced **client-side in the Node runtime**: (a) cross-process filesystem lock dir per host:port (`revit-mcp-command-locks`, 8 s wait, 10 min stale — ConnectionManager.ts:43-46, 276-321) and (b) an `mcp_status` busy preflight before every command that throws "revAgent is busy with …" if a task is active (SocketClient.ts:279-304; served in-plugin without registry dispatch at SocketService.cs:522-526, backed by in-memory single `_activeTask` — McpTaskStatusService.cs:109-118). **O1 consequence:** the serial-per-session guarantee and busy semantics are Bridge responsibilities to port, not add-in features. Minor race worth fixing during adaptation: `ExecuteCodeEventHandler.WaitForCompletion` calls `_resetEvent.Reset()` before waiting (ExecuteCodeEventHandler.cs:43-47) — can drop an already-signaled completion.

- **Registry:** `RevitCommandRegistry` = plain `Dictionary<string, IRevitCommand>` keyed by `CommandName` (src/revit-plugin/revAgentPlugin/Core/RevitCommandRegistry.cs:8-27). - **Inventory:** **21 commands**, all in `revAgentCommandSet.dll`, snake_case names (source manifest src/revit-plugin/revAgentCommandSet/command.json:10-116): get_current_view_elements, get_current_view_info, get_selected_elements, send_code_to_revit, list_open_views, activate_view, close_view, clear_selection, delete_review_view, get_ui_state, find_elements, inspect_levels, inspect_sheet_text, inspect_schedules, count_annotations, extract_spatial_snapshot, get_spatial_change_state, open_existing_plan_for_element_level, focus_elements, section_box_elements, create_3d_view_for_elements. The Node runtime fans 44 MCP tools (installer/runtime-mcp-server/src/tools/, 8 of them wrapping `send_code_to_revit`) onto these 21 commands — the wide/parameterized-command shape D5/5.3 wants already exists at this boundary.
- **Transactions today:** per-command `Transaction` opened inside the event handler, only where writes occur; no groups. Evidence: ExecuteCodeEventHandler.cs:75 (`"Execute AI code"`, with `transactionMode: auto|none` param, ExecuteCodeEventHandler.cs:20-21, 56-87, and a regex guard blocking model-authored manual `Transaction|SubTransaction|TransactionGroup` unless `transactionMode=none`, 137-148); DeleteReviewViewEventHandler.cs:213; SectionBoxElementsEventHandler.cs:270; Create3DViewForElementsEventHandler.cs:319, 391. All other commands are read-only/UI-only (e.g. GetSelectedElementsEventHandler — no Transaction).
- **Error propagation:** two distinct channels the runtime already distinguishes: (a) JSON-RPC `error` (transport/dispatch/exception — SocketService.cs:609-625 wraps handler exceptions as `InternalError` with `ex.Message`; client rejects on `response.error`, SocketClient.ts:359-364); (b) application-level result payloads returned as JSON-RPC *success* but carrying `success:false` / `guarded:true` / `guardReason` / `errorMessage` fields (contract sniffed at SocketService.cs:758-833; e.g. ExecutionResultInfo ExecuteCodeEventHandler.cs:299-315). O1's structured retryable-vs-terminal error taxonomy must subsume both channels.

## 3) Batch as one TransactionGroup — what the add-in needs

- **Existing TransactionGroup usage: none.** The only occurrence of `TransactionGroup` in the codebase is the guard regex in ExecuteCodeEventHandler.cs:146. Grep across src/ confirms only per-command `new Transaction(...)` at the five sites listed above.
- **Closest seam:** the dispatch point SocketService.cs:529-564 (single method → single command → single ExternalEvent round-trip) plus the handler layer's uniform `IExternalEventHandler.Execute(UIApplication)` signature (e.g. ExecuteCodeEventHandler.cs:49).
- **What a batch requires:** (1) a new envelope (either JSON-RPC batch array — currently unsupported, parser expects one object (SocketService.cs:505) — or, cleaner, a new registered command e.g. `execute_batch` with `params.invocations[]`, avoiding any SDK/framing change); (2) a single batch ExternalEvent handler that, on the UI thread, opens `TransactionGroup` → for each sub-invocation resolves the target command's handler, sets its parameters, calls its `Execute(app)` **directly** (already on the API thread), collects per-item results → `Assimilate()` on success / `RollBack()` on failure policy. Per-command `Transaction`s nest legally inside a `TransactionGroup`, so existing handlers need no transaction changes. (3) The required refactor: today parameter-setting + result-reading is fused with the marshal/wait cycle inside each `*Command.Execute` (calling `RaiseAndWaitForCompletion` from the batch handler would deadlock the UI thread). Extract a `Prepare(JObject)/ExecuteCore(UIApplication)/Result` seam per command — mechanical, since every command already follows exactly that internal shape (ExecuteCodeCommand.cs:26-54, GetSelectedElementsCommand.cs:26-53). (4) UI-context caveat: some commands drive view activation/UIDocument state (activate_view, focus_elements, create_3d_view_for_elements) — batch spec must define ordering semantics for UI-affecting members and whether they are batchable at all.

## 4) Idempotency — none exists

No invocation-id, dedup, or durable journal anywhere in the add-in or runtime. Correlation is the JSON-RPC `id` only. `McpTaskStatusService` is in-memory status/metrics (single `_activeTask`, last 100 tasks — McpTaskStatusService.cs:109-118), never consulted for dedup and lost on Revit restart. The "journal" hits in Spatial code (GetSpatialChangeStateEventHandler.cs, SpatialSnapshotHelpers.cs:459-461) are a model-change-sequence tracker for snapshot liveness, unrelated to invocation idempotency. One redelivery-shaped behavior to retire: the client's framing fallback re-sends the identical request once in legacy framing after a framing error (SocketClient.ts:325-333). Conclusion for O1/5.4: the idempotency journal is greenfield and belongs entirely in the Bridge, keyed on the Gateway-issued invocation id; the add-in stays journal-free (its single-flight busy model plus Bridge-side journal covers the D-spec).

## 7) MINIMAL adaptation list — add-in's peer becomes the Bridge

The add-in is a passive TCP JSON-RPC server with zero knowledge of its peer: no auth, no client identity, no handshake, no persistent connection assumption (SocketService.cs:224-230, 243-313). A Bridge that speaks the same 4-byte-BE length-prefixed JSON-RPC 2.0 dialect connects with **zero required add-in code changes** — protocol-level change set is empty.

Strictly required (protocol): **nothing.** Config only: Bridge reuses the existing discovery contract — env `REVAGENT_PLUGIN_PORT`/`REVAGENT_PORT` (SocketService.cs:88-92) or `settings.port` in commandRegistry.json (ServiceSettings.cs:20), plus the +20 port auto-increment scan for multi-session (SocketService.cs:149-185; today's scan list ConnectionManager.ts:263-265).

Required to ship the target's feature set (add-in changes, all additive):
1. **Loopback binding (should ride the cutover):** change `IPAddress.Any` → `IPAddress.Loopback` at SocketService.cs:157. Today the add-in is an unauthenticated LAN-reachable arbitrary-code endpoint (`send_code_to_revit`); once the only legitimate peer is the local Bridge, non-loopback binding is pure attack surface. One-line change + optional env escape hatch.
2. **`execute_batch` command with TransactionGroup semantics** (Section 3): new command DLL entry + the Prepare/ExecuteCore seam refactor across the 21 commands. This is the only structural add-in work in the whole migration.
3. **Optional handshake enrichment:** extend `mcp_status` snapshot (SocketService.cs:522-526 / McpTaskStatusService) with plugin version + `resultContractVersion` + Revit version + open-document identity, so the Bridge can populate session registration (5.4) from one probe. Additive fields; existing get_ui_state/get_revit_session_context already cover document context if this is deferred.
4. **Invocation-id passthrough: no change needed.** Commands read only named keys from `params` (SocketService.cs:716-756; per-command JObject access), so a Bridge-added `invocationId` param is silently tolerated today; echoing it in results is optional polish.

Must be ported into the Bridge from the retiring Node runtime (no add-in impact, but load-bearing for correctness): per-target command lock (ConnectionManager.ts:276-321), `mcp_status` busy preflight (SocketClient.ts:279-304), connect-per-operation or (better) persistent-connection management with the framing writer/reader (SocketClient.ts:53-211, 396-406), port/instance discovery (ConnectionManager.ts:214-274), timeout ladder (SocketClient.ts:287, 378). Deliberately dropped: legacy-JSON framing fallback (SocketClient.ts:316-339) — freeze the Bridge on length-prefixed only.

Explicitly unchanged (per doc §9): framing layer (SocketService.cs:336-367, 454-468), JSON-RPC envelope + resultContractVersion contract (BridgeResultContract.cs), registry/dispatch (RevitCommandRegistry.cs, CommandManager.cs), all 21 command implementations and their per-command transactions, ExternalEvent marshaling (ExternalEventManager.cs).
