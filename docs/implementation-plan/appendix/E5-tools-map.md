## 3) Dynamic-tool-promotion mechanism — semantics and verdict

- **What it is:** an offline usage-analytics feedback loop, not a runtime loading mechanism. `config/dynamic-tool-promotion-rules.json` defines `repeatThreshold: 2` and three trigger signals: `repeated_hash` (same dynamic C# snippet hash seen ≥ threshold), `write_patterns_present`, `manual_transaction`. `config/dynamic-tool-promotion-registry.json` defines lifecycle states (`candidate`/`promoted`/`watch`/`rejected`) and three pattern entries with candidate actions (e.g., `design_native_tool_with_preflight_and_verification`, `move_transaction_boundary_to_runtime_tool`).
- **Who consumes it:** only the admin usage-intelligence PowerShell summarizer — `addons/usage-intelligence/scripts/summarize-usage-intelligence.ps1:265-295` loads both files; lines 1613, 1703-1709 compute the reasons from telemetry events of `send_code_to_revit`/`send_code_to_revit_safe` usage; line 2016: "Repeated send_code is human-review evidence only." Nothing in the TS runtime reads these files.
- **Relation to deferred loading: none.** It does not gate which tools are exposed to the LLM; it flags *which dynamic C# snippets should be promoted into first-class native tools* (this is visibly how inspect_schedules, count_annotations, set_schedule_cells etc. were born). AGENTS.md:71-75 and SKILL.md ("Usage-intelligence promotion signals are review evidence, not permission...") both instruct the agent that promotion signals never authorize writes or priority escalation.
- **Verdict for the plan:** it is a **tool-lifecycle/roadmap signal, not a proto-capability-index — do not build the D5 index on it, but do not discard the concept.** Target mapping: (a) the trigger signals become derived metrics of the O7 telemetry event schema (Mode-B sandbox scripts are the new "dynamic snippets" — the same repeated-hash detection applies to generated code); (b) the registry states (candidate/promoted/watch/rejected) fold into the Tool Registry as tool-lifecycle metadata; (c) the two JSON config files and the PS summarizer path are retired with the NAS-era usage-intelligence pipeline (O11 metric-parity check must cover the promotion signals: send_code counts, repeated-hash groups, write-guard/manual-transaction events).

## 5) evals/ — contents and reuse as the Gateway regression suite

`evals/evals.json` (~22.3 KB, `skill_name: revAgent`, 13 evals) + `evals/schemas/spatial-phase1b-agent-evidence-v2.schema.json` (agent-evidence contract, cross-checked by `installer/runtime-mcp-server/scripts/spatial-phase1b-eval-contract.test.mjs`). Two groups:

- **Spatial grounding protocol evals (suite `spatial_grounding_phase1b`, ids 101-105, 201-202, 401, 501-502, 601):** each has a `context` fixture (snapshot with liveness current/stale/unknown, partial/coverage flags, operation results with basis/precisionClass/verdictCapability), plus `required_tool_calls`, `forbidden_tool_calls` (always banning send_code_*, all write tools, delete_review_view, and NAS lifecycle names), `hard_fail_if` conditions, and soft `assertions`. They test tool-selection discipline and evidence-citation guardrails: abstain without a snapshot (101), refuse global claims from partial coverage (102), refuse current-state claims from stale/unknown liveness (103/104), cite snapshot+revision ids on historical diffs (105), cite node ids/basis/precision (201), advisory ≠ verification (202), never do coordinate arithmetic in the LLM (401), context_only/screening_only never promoted to verdicts (501/502), derived nodes labeled as inference with confidence+sources (601).

**Seeding the Gateway regression suite (Mode A vs Mode B):** the eval format already is a loop-level harness spec — prompt in, required/forbidden tool invocations + hard-fail predicates out. Reuse plan: (a) replay all 13 through the Orchestration Engine in **Mode A** asserting required/forbidden calls against the audit event stream (the D5 twist: required tools must first be *discovered from the one-line capability index*, making these the first deferred-loading accuracy evals for free); (b) replay in **Mode B** asserting the sandbox script calls the equivalent tool wrappers and never computes spatial relations inline — codegen evals 1-4 apply almost unchanged to Mode B script generation; (c) run A and B on identical prompts and diff outcome + token cost + latency — the comparison metric D5's mode-routing needs. **Gaps to add as new suites:** planner/router classification (discipline + data-plane + complexity, 5.2 stage 2), policy-class enforcement (confirm preview actually blocks until approval; forbidden_tool_calls generalizes into per-eval policy fixtures), context-projection invariant (turn-30 ≈ turn-3 size), result-ref paging behavior, and per-discipline namespace isolation (mech eval must never see struct tools in context). The `forbidden_tool_calls` NAS names (`publish_nas_release` etc.) are already-dead vocabulary retained only in the eval contract; retire with the NAS.
