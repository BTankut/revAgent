# P6 — APS Integration Work Package (O4; arch §5.6 reviewer data plane; D7 twin modeling)

## (a) Scope & Non-Goals

**Scope.** Everything needed to stand up the *published-model* data plane on Autodesk Platform Services: APS app registration and OAuth flows; a token-lifecycle service inside the Gateway; AEC Data Model (GraphQL) read twins of the existing schedule/quantity tools; a Design Automation for Revit (DA4R) appbundle pipeline built from the existing C# codebase for exact-schedule export and batch model writes; the reviewer UX truth rule (published-version banner); and APS-specific rate/cost controls wired into the O7 event schema.

**Phase determination (confirmed against the migration plan).** The ENTIRE APS plane is **Phase 2 (post-cutover)**. Grounds: (1) `docs/TARGET_ARCHITECTURE.md:202` — "Freeze feature development for the duration" of the D11 migration; (2) the reviewer persona is not served by the current system at all (zero APS code exists in the repo — verified: no match for `executorBinding|'aps'|"aps"` anywhere; `config/dynamic-tool-promotion-registry.json` is an unrelated registry for dynamic-code→native-tool promotion states, lines 4–9), so cutover parity does not require APS; (3) the D11 pilot validates only the bridge path (`docs/TARGET_ARCHITECTURE.md:205`). **Phase 1 carries exactly two thin seam-reservation tasks (P6-T1/T2, ~2 dev-days) executed inside the registry/data-model packages' schemas — no APS runtime code in Phase 1.**

**Correction for the coordinator:** the working assumption "executor-binding enum already contains 'aps'" is FALSE in the current codebase. That seam does not exist yet; it must be *created* by the Phase-1 Tool Registry package (arch §5.1.3 requires executor binding `bridge/APS/internal`). P6-T1 below is the review-and-sign-off obligation on that package, not new code here.

**Non-goals.**
- No Revit-on-web embedding, no APS Viewer integration (visual review UX is out; text/tabular results only in this package).
- No ACC Issues/RFI/Submittals APIs, no webhooks-driven model-publish automation (candidate for a later package).
- No change to the live data plane: bridge, add-in, TCP framing, all 35 existing tools (`installer/runtime-mcp-server/src/tools/register.ts:76`) stay as-is per arch §9.
- `send_code_to_revit` / dynamic LLM-generated code NEVER executes on the APS plane (see P-APS-6). DA activities are fixed, versioned templates only.
- No migration of historical data; no Phase-1 feature work beyond seam reservation.

## (b) Plan-Level Design Decisions (proposals; do not conflict with closed D1–D12)

- **P-APS-1 — Twin modeling: one logical tool, per-plane variants.** The registry stores a logical tool id (e.g., `common.elements.find`) with a `variants[]` array: `{plane: "live"|"published", executor: "bridge"|"aps"|"internal", schema_overlay, fidelity_notes[]}`. The capability index (arch §5.2.1) renders the logical tool once; the planner/router (arch §5.2.2) picks the plane; dispatch resolves the variant. *Rationale:* keeps D7's two planes from doubling the capability index and gives the router a single decision point instead of the LLM choosing between near-duplicate tools.
- **P-APS-2 — OAuth split: 3-legged (auth code + PKCE) for all user-context data access (AEC DM reads, DA4R jobs opening ACC cloud/workshared models per arch §5.6:142); 2-legged client-credentials for DA service management (appbundles/activities/work items), OSS transfer buckets, and webhook administration.** Scopes minimal: `data:read data:write` (3LO), `code:all bucket:create bucket:read data:read data:write` (2LO). One APS app per Gateway deployment variant (SaaS app vendor-owned; on-prem/VPC tenants may register their own app — app credentials are 12-factor config per arch §7:194). *Rationale:* matches Autodesk's access model — ACC model data is user-entitled, service plumbing is app-entitled; per-variant apps keep the on-prem edition credential-sovereign.
- **P-APS-3 — Token vault in Postgres, tenant-scoped, encrypted at rest.** New tables `aps_user_grant` (user_id, tenant_id, encrypted refresh token, scope set, consent timestamps, revoked_at) and in-memory (per-process) access-token cache with expiry skew; 2LO tokens cached per-tenant-app, never persisted. All rows carry `tenant_id` (arch §5.9:168). *Rationale:* refresh tokens are the highest-blast-radius secret after the LLM key; they live only in the data layer the arch already mandates, never in bridge or client.
- **P-APS-4 — Two-tier schedule strategy on the published plane.** Tier 1 (seconds): derived quantity/BOQ tables computed gateway-side from AEC DM GraphQL element+property queries — covers the dominant reviewer use cases already encoded in `evals/evals.json` (eval 1: pipe BOQ by system type/diameter; eval 2: duct lengths grouped by classification/size). Tier 2 (minutes, batch): exact `ViewSchedule` export via a DA4R activity, because **AEC DM does not expose Revit schedule views** — this is the single biggest fidelity gap vs `inspect_schedules`. The router advertises Tier 1 as the default twin and Tier 2 as an explicit "exact schedule export (batch job)" tool. *Rationale:* preserves interactive latency for the 80% case while keeping schedule fidelity available; never silently substitutes derived numbers for a formatted schedule.
- **P-APS-5 — Headless core extraction, not a rewrite.** Every C# command today is an `ExternalEventCommandBase` + `IExternalEventHandler` pair whose only UI dependency is document acquisition (`src/revit-plugin/revAgentCommandSet/Commands/View/InspectSchedulesEventHandler.cs:142-143` — `app.ActiveUIDocument.Document`; request/result POCOs are already UI-free, lines 13–80). Refactor pattern: extract `XCore.Execute(Document, XRequest) : XResult` static cores; the desktop event handler becomes a thin adapter; a new appbundle project consumes the cores under `IExternalDBApplication` + `DesignAutomationBridge`. The appbundle project must NOT reference `RevitMCPSDK` or use `RevitAPIUI` types (current csproj references both: `src/revit-plugin/revAgentCommandSet/revAgentCommandSet.csproj:49-53`), no `ExternalEvent` (44 files currently use it — all in the adapter layer, which stays desktop-only), no `SocketService`/`ExternalEventManager` (`src/revit-plugin/revAgentPlugin/Core/`). *Rationale:* arch §9:214 forbids rewriting the add-in; extraction reuses proven scan/filter logic (the "filtering happens in the C# add-in" rule, arch §5.3:124) on both planes.
- **P-APS-6 — No dynamic code on the APS plane; structured-writes-only DA activity.** The live write tools (`set_element_parameter`, `set_schedule_cells*`) are code generators executed through the dynamic-code engine (`installer/runtime-mcp-server/src/tools/set_element_parameter.ts:796`, `set_schedule_cells.ts:392` → `ExecuteCodeEventHandler` with auto-transaction wrapping and manual-transaction guard, `src/revit-plugin/revAgentCommandSet/Commands/ExecuteDynamicCode/ExecuteCodeEventHandler.cs:56-75,137-146`). The published-plane write twin is instead a **data-driven** DA activity: structured write-set JSON in → deterministic C# applies within one transaction → diff report out → saves a new cloud model version. The registry enforces that any tool tagged `dynamic_code` can never bind executor `aps`. *Rationale:* D12 ("LLM proposes, engine verifies") and the liability chain; shipping LLM-generated code into an unattended cloud Revit engine is an unacceptable failure mode.
- **P-APS-7 — Published-version banner as a data contract, not a UI nicety.** Every published-plane tool result carries mandatory metadata `{dataPlane:"published", versionUrn, versionNumber, publishedAt, publishedBy}`; the web client renders the banner from it; the audit event (arch §5.1.4) stores it; cross-plane comparisons must label both sides. Enforced by a runtime schema check in the APS executor — a result without version metadata is an error. *Rationale:* arch §5.6:143 makes live-vs-published a product truth; making it a validated contract keeps it from eroding.
- **P-APS-8 — Reconcile pipeline gets the APS twin through its existing source-adapter seam.** `adaptScheduleSource` already takes a discriminated source (`kind:"inspect_schedules_result"` | `kind:"revit_schedule"`, `installer/runtime-mcp-server/src/tools/reconcile_schedule_adapter.ts:61,146`) with an injectable transport (`sendCommand?: typeof sendRevitCommand`, line 143); ingestion/normalization/matching (`reconcile_excel_ingestion.ts`, `reconcile_matching.ts`) never touch Revit. Add `kind:"aec_dm_quantity_table"` producing the same normalized shape. *Rationale:* the procurement/fabrication reviewer workflow (Excel↔schedule reconciliation) becomes plane-agnostic with a single adapter case, zero changes to matching logic.
- **P-APS-9 — DA jobs are metered, quota'd, and previewed.** Per-tenant concurrency cap and daily work-item budget; pre-flight estimate (engine minutes ≈ f(model size, activity)); every work item emits O7 events (`aps.workitem.submitted/completed` with engine time + credit cost, `aps.graphql.request` with complexity); AEC DM calls go through a per-tenant token bucket; GraphQL responses cached keyed by version URN (published versions are immutable → caching is sound). *Rationale:* DA4R bills per engine-hour in cloud credits/Flex — an unbounded agent loop submitting jobs is a direct cost incident; arch §5.10:179 requires every needed metric to be an O7 event.
- **P-APS-10 — APS executor implements the same executor interface as the bridge executor.** The Gateway dispatch layer (arch §5.2.4) sees `bridge | aps | internal` behind one interface: `execute(invocation) → result|structured_error`, with per-class retry policy (APS retryable; arch §5.2.4:108). Module boundary: `gateway/src/aps/` = {token service, ACC resource resolver, AEC DM client, DA job service, executor adapter}. *Rationale:* keeps the orchestration engine plane-blind and lets Phase-1 dispatch ship with a stub `aps` executor returning `executor_unavailable`.

## (d) Test Strategy

1. **Recorded-fixture contract tests (fast, offline):** AEC DM GraphQL and DA REST interactions recorded once against real APS, replayed in CI (the repo already uses the fixtures pattern: `installer/runtime-mcp-server/scripts/fixtures/`). Token service tested with a mock OAuth server: refresh races, expiry skew, revocation, cross-tenant denial.
2. **Live-vs-published parity harness (the core correctness instrument):** publish a golden office model to ACC; run each read twin against both planes (bridge on a workstation vs APS) and diff normalized outputs. The reconcile adapter's injectable transport (`reconcile_schedule_adapter.ts:143`) and pre-fetched-source mode (`kind:"inspect_schedules_result"`) make the reconcile pipeline testable with either plane's output without Revit. Parity gaps must match the P6-T13 fidelity matrix — an undocumented gap is a failing test.
3. **DA canary pipeline:** every appbundle publish to the dev alias auto-submits a smoke work item per supported engine version (2022–2025) against a canary cloud model; prod alias promotion requires green canary + green parity. Runs on the existing `revagent-cd` self-hosted Windows runner (no DA emulation exists; the canary is the integration test).
4. **Write-safety tests:** BatchParameterWriteActivity property-based tests on write-set application (idempotent re-apply, partial-failure rollback = transaction rollback, diff-report completeness); confirm-gate flow tested at the orchestration level (approval token required, replay rejected). Registry-level test that `dynamic_code` tools cannot be bound to executor `aps`.
5. **Eval reuse:** the existing BOQ/quantity evals (`evals/evals.json` ids 1–2) become dual-plane evals — same natural-language prompt, expected equivalent quantities from Tier-1 derived tables; guards against the twin drifting semantically from the live tools.
6. **Security tests:** token vault encryption at rest verified, tokens absent from logs/audit/telemetry (grep-based CI check on structured log schema), scope minimization asserted against the APS app config, tenant isolation on every APS code path.
7. **Chaos/edge:** webhook duplicate + out-of-order delivery, DA timeout/engine-crash mapping, APS 429/5xx → retry policy (retryable class), circuit-breaker trip/recovery, stale-version detection (model republished mid-session → banner metadata updates on next call).

## (e) Package-Specific Risks

1. **AEC DM coverage gaps (highest).** No schedule-view exposure; published-model support is Revit 2024+ only (arch §5.6:141) while the fleet builds R22–R25 (`revAgentCommandSet.csproj:10-36`) — customers publishing from Revit 2022/2023 get no Tier-1 plane at all; property/filter coverage varies by category. *Mitigation:* P6-T13 parity spike is scheduled first among the read work; fidelity_notes drive structured "not supported" errors; Tier-2 DA fallback covers schedule fidelity and, if the spike fails badly, can be widened into a "DA-extract-then-query" fallback plane for pre-2024 models (scope change, flagged to coordinator).
2. **DA latency/cost shape mismatch with agent UX.** Work items take minutes and bill engine time; an agentic loop treating them as ordinary tools burns credits and stalls turns. *Mitigation:* P-APS-9 quotas + pre-flight estimates; DA tools are described in the capability index as batch jobs with async result delivery; orchestration failure semantics (arch §5.2:114) cap retries at zero for cost-bearing jobs without user re-approval.
3. **3LO consent + refresh-token decay for occasional reviewers.** Reviewers use the product sporadically; expired/revoked grants surface exactly when a consultant needs an answer. *Mitigation:* re-consent is a first-class flow in P6-T11 with a clean in-chat prompt; grant-health surfaced in the admin dashboard; 2LO is never used as a workaround for user-entitled data.
4. **Headless extraction regression risk on the live path.** P6-T16 touches the proven handlers (44 ExternalEvent-using files). *Mitigation:* extraction is mechanical (Document-core split at the `app.ActiveUIDocument.Document` seam, `InspectSchedulesEventHandler.cs:142-143`), done behind unchanged public command contracts, gated by the live regression suite, and scheduled post-cutover when the bridge path is the monitored production path.
5. **APS platform volatility.** AEC DM GraphQL schema is still evolving; DA engine versions rotate yearly. *Mitigation:* pinned schema snapshot + contract tests (drift breaks CI, not production); appbundle matrix already parameterized by RevitVersion; canary catches engine changes at publish time.
6. **Version-truth erosion.** Reviewers acting on stale published versions is a liability-chain hazard for a product whose audit trail is a selling point (arch §6:186). *Mitigation:* P-APS-7 makes version metadata a validated contract enforced in the executor, not a UI convention; audit stores it per invocation.
7. **Secret blast radius.** The token vault concentrates cross-customer ACC access in one table. *Mitigation:* encryption at rest with keys outside the DB, tenant_id row scoping, access audited, on-prem variant keeps grants on customer infrastructure by design (P-APS-2 per-variant apps).
8. **Coordination risk on Phase-1 seams.** If the registry package ships a two-value executor enum or omits `variants[]`, Phase 2 starts with a schema migration instead of feature work. *Mitigation:* P6-T1 is a blocking sign-off inside the freeze window, costed and assigned now.
