# P2 — Gateway Core: Orchestration Engine, LLM Provider Layer, Tool Registry, Context Strategy (arch doc §5.1–5.3)

## (a) Scope & non-goals

**In scope**
- The Gateway service skeleton (process model, module layout, config, container build entry) per arch doc §5.1 subsystems 1–3.
- Relocation of the Node/TS runtime's 35 tool implementations (`installer/runtime-mcp-server/src/tools/`, registered at `installer/runtime-mcp-server/src/tools/register.ts:39-77`) into a shared package consumed by the Gateway, without rewriting tool code (§9: "all tool implementations" do not change).
- Tool Registry: data model, build-time schema harvesting from the existing zod definitions, capability-index generation, policy-class + executor-binding + namespace metadata (feeds D5/D6/D12), versioned SKILL/AGENTS serving.
- Orchestration Engine: the five-stage request lifecycle (§5.2), Mode A (deferred schemas / tool-search), context projection engine with the turn-30≈turn-3 invariant, result hygiene with `result_ref` paging, guardrails enforcement (auto/confirm/gated incl. the confirm round-trip), failure semantics, sub-agent mechanism (post-pilot), planner/router stage (post-pilot, optional).
- LLM Provider Layer: OpenAI-compatible adapter contract, per-model capability flags, streaming, basic quota/queue.
- North MCP surface wiring (Streamable HTTP via `@modelcontextprotocol/sdk` ^1.29.0, already a dependency — `installer/runtime-mcp-server/package.json:75-84`), so Phase-1 interim clients (O8, e.g. Claude Code) can drive the Gateway before the web client matures.
- Mode B (code execution): **interface stubs only** (see P-GW-8); O2 design is a later work package.

**Non-goals (owned by sibling packages; P2 consumes their interfaces)**
- Bridge↔Gateway protocol implementation and the bridge itself (O1 package). P2 defines and consumes an `Executor`/`RevitTransport` interface and develops against a fake + the existing local-TCP path.
- Auth·Licensing·Audit subsystem internals (OIDC, device tokens, seats — O3/O5 package). P2 consumes an `AuthContext` interface and an entitlement query.
- APS integration (O4), web chat client (O8), admin-plane migration (O11), deployment/Compose/warm-standby (Phase-1 ops package, O10), bridge self-update (O9), CSI module internals (only its `gated` policy hook is provided here).
- Mode B sandbox internals (O2), historical data migration (closed: none).
- No new end-user features: feature freeze per §8 holds; every task below is migration/relocation work.

## (b) Plan-level design decisions

**P-GW-1 — Gateway is a TypeScript/Node event-loop service (Fastify + node:http, ESM, Node 22 LTS).** Justification vs alternatives: the entire tool layer — 75 TS files, ~26k lines, all input schemas as inline zod objects, all C# codegen helpers — already exists in TypeScript ESM (`installer/runtime-mcp-server/`), and §9 pins "all tool implementations" as unchanged; any non-Node gateway (Go, C#/.NET, Python) would force either a rewrite of that layer or an awkward out-of-process hop between orchestration and tools, recreating the very IPC the architecture removes. The Gateway is explicitly I/O-bound (arch doc §6: waits on LLM seconds and bridge results), which is Node's home turf; the MCP SDK with `StreamableHTTPServerTransport` for the north boundary is already a pinned dependency; zod schemas are simultaneously the runtime validators and the source for LLM-facing JSON Schema generation, which no other stack gets for free. Fastify over NestJS (no DI framework needed for ~10 modules; keeps 12-factor config trivial) and over Express (native async, schema-validated routes, better perf under streaming).

**P-GW-2 — Monorepo workspace split; the old stdio runtime becomes a thin shell over a shared `packages/revit-tool-core`.** `git mv` `installer/runtime-mcp-server/src/{tools,utils,spatial}` (minus dead code) into `packages/revit-tool-core/`; `installer/runtime-mcp-server/src/index.ts` (currently 29 lines, stdio wiring at `index.ts:13-20`) keeps building the same `build/index.js` bin from the shared package, so the frozen NAS-deployed path is bit-compatible in behavior until cutover (D11: old path never removed before the new path carries traffic). Deletions in the move: `src/database/db.ts` + `service.ts` (zero importers) and the `ws` dependency (declared, never imported).

**P-GW-3 — Tool onboarding via a `RegistryCollector` that implements the existing `ToolServer` interface — zero edits to the 35 tool files.** Every tool registers through `server.tool(name, description, zodShape, handler)` against the 13-line interface at `installer/runtime-mcp-server/src/tools/types.d.ts:10-22`. The Gateway provides a collector implementing that interface which captures `(name, description, zodShape, handler)` into registry records instead of an MCP server; `registerTools()` runs unmodified. The same interception seam already proven by `wrapServerWithTelemetry` (`src/utils/telemetry.ts:1820-1935`) is reused for the Gateway's dispatch middleware chain.

**P-GW-4 — Registry = code-defined truth for schema+handler, DB-resident truth for governance.** Build step runs the collector, serializes zod→JSON Schema (`zod-to-json-schema`), and emits a content-hashed `registry-seed.json` artifact per module; a deploy-time sync job upserts `tool` / `tool_version` rows. Policy class, namespace, executor binding, entitlement mapping, and deprecation state live in Postgres and are editable without redeploy; schema/handler changes require a new seed (new `tool_version` row keyed by content hash). The E5 table (35 tools → `core.*` names, policy classes, S/M/L schema sizes) is the initial metadata authoring input. The existing `config/dynamic-tool-promotion-registry.json` + `-rules.json` (dynamic-C#→native-tool promotion candidates) folds in later as `tool_candidate` records — same governance store, no separate file.

**P-GW-5 — Per-invocation execution context via `AsyncLocalStorage`; executor binding resolved at the two existing chokepoints.** All 30+ Revit-bound tools reach the socket exclusively through `executeRevitCode` (`src/utils/revitToolHelpers.ts:369`) and `sendRevitCommand` (`:472`; plus `get_selected_elements` at `:604` which calls the latter). These two functions are re-pointed at a `RevitTransport` interface with three implementations: `FakeRevitTransport` (test), `LocalTcpTransport` (wraps today's `withRevitConnection`, `src/utils/ConnectionManager.ts:323-366`, kept for the stdio shell and dev harness), and `BridgeSessionTransport` (O1 client, delivered by the bridge package). Tenant, session, bridge-session id, idempotency key, policy decision, and audit correlation ride an `InvocationContext` in `AsyncLocalStorage` so the `(args, extra)` handler signature of all 35 tools stays untouched.

**P-GW-6 — LLM-visible schemas are derived by stripping the two mixins; routing/audit fields are injected server-side.** `connectionTargetSchema` (target/host/port) and `taskMetadataSchema` (taskName/taskId/parentTaskName/parentTaskId) at `src/utils/revitToolHelpers.ts:50-65` disappear from every LLM-facing schema (≈7 params × 35 tools of context removed); the dispatcher merges session-routing and audit fields into `args` before invoking the handler. Handlers keep reading them via `connectionOptionsFromArgs`/`taskOptionsFromArgs` (`:75-98`) unchanged.

**P-GW-7 — Mode A = capability index in the cached static prefix + two meta-tools (`tool_search`, `tool_schema`) + a pinned non-deferred core set.** Pinned set (per D5's "3–5 core tools"): `core.element.query` (find_elements), `core.document.context` (get_revit_session_context), `core.view.context` (get_active_view_context), `core.session.status`. `tool_search(query)` ranks over name + description + argument names (D5: naming is API design); `tool_schema(names[])` returns full JSON Schema and marks those tools callable. Loaded-schema set is session-sticky, lives in a projection segment *after* the cache boundary, and is evicted LRU beyond a budget. Deferral is implemented in-house on the OpenAI-compatible contract (D8), not via any provider-native tool-search feature.

**P-GW-8 — Mode B ships as interfaces only in this package.** Stubbed now: (i) `EngineMode` interface (`prepareTurn(projection) → ProviderRequest`, `interpretResponse(resp) → EngineAction[]`) with `ToolCallingMode` implemented and `CodeExecMode` throwing `NotImplemented`; (ii) `SandboxHost` interface (`createSession(scope)`, `exec(script, limits) → {stdout, summaries}`, `toolRpcEndpoint`); (iii) registry function signature `generateToolWrapperTree(registryView) → FileManifest` (wrapper file tree from schemas); (iv) per-model capability flags `supports_tool_search` / `supports_code_exec` in the provider layer config. Everything else (runtime choice, egress policy, resource limits, filesystem layout) is O2, deferred.

**P-GW-9 — Context is a pure projection function over server-side session state, in six segments.** `project(sessionState, budget) → ProviderMessages`: S1 static prefix (system instructions from versioned instruction docs + capability index — the prompt-cache boundary, hash-pinned per session so mid-session registry edits don't bust the cache); S2 session pin (bridge-supplied document context, discipline hint); S3 rolling summary of evicted turns (written asynchronously post-turn by a cheap model); S4 verbatim recent window (last K turns); S5 loaded tool schemas (Mode A); S6 working set (active `result_ref` digests). Old tool results are replaced by digest+ref, never appended. Invariant measurement: every turn emits `projection_tokens{segment}` into the O7 event stream, and a CI eval replays scripted 30-turn sessions asserting max(projected tokens, turns 10–30) ≤ 1.10 × max(turns 3–9) — the invariant is a red/green gate, not an aspiration.

**P-GW-10 — Result hygiene is a post-handler dispatch interceptor layered above the tools' existing budget guards.** Tools already truncate server-side (find_elements compact/budget modes; `trimPlanCandidatesInPayload` at `revitToolHelpers.ts:264-296`; bounded readers in inspect_schedules/inspect_sheet_text). The interceptor measures serialized result size; above threshold (initial 16 KB) it persists the full payload to the object store, records a `result_ref` row, and hands the model `"N items, ref:R17, first page shown"`. Paging via meta-tool `result_page(ref, cursor, limit)`; refs are session-scoped, TTL-bound, tenant-isolated. In Mode B this layer becomes mostly free (arch §5.2.5) — the interface anticipates that by keying refs identically in both modes.

**P-GW-11 — Guardrails are enforced only at the dispatcher, keyed to the registry's policy class — never trusted from model, client, or args.** Middleware order at stage 4: policy → entitlement → idempotency → executor. `auto` proceeds (view-scope writes are audit-flagged per E5). `confirm`: dispatcher does *not* execute; it runs the tool's existing preview path (the write tools already default to dry-run: `set_element_parameter` dryRun-by-default, `set_schedule_cells*` preview modes, `delete_review_view` dry_run/commit+confirmDelete at `src/tools/delete_review_view.ts:66`), stores a single-use `pending_action` (id, session, tool, args-digest, preview payload, TTL 10 min), and returns a structured `confirmation_required` result. Approval round-trip per client: web/chat API → explicit `POST /sessions/:id/actions/:id/approve`; north-MCP clients → MCP elicitation when the client supports it, otherwise the result carries an authenticated approval URL (out-of-band click) — because an external LLM could otherwise call a `confirm_action` tool itself. Approval executes against the stored args-digest (you approve exactly what was previewed). `gated` (CSI): same primitive with `gate=true` — never approvable in-channel, never auto-approvable by config, requires the out-of-band path + role check; tenant-tightenable via a policy-override table (tenant may promote `auto`→`confirm`, never demote). The 21 write-pattern regexes in `src/tools/send_code_to_revit_safe_guards.ts:1-27` additionally run gateway-side as a pre-dispatch validator on `core.code.execute` payloads regardless of claimed intent.

**P-GW-12 — Structured failure taxonomy + bounded loop.** Every dispatch error is normalized to `{retryable, class: parameter|environment|policy|timeout|conflict, executor, detail}` and returned to the model as a structured tool error. Engine breaks the loop after 3 consecutive failures of the same plan step and emits a clean user-facing explanation. Revit-bound writes are never auto-retried; on redelivery ambiguity the dispatcher consults the bridge idempotency journal (O1 `journal_lookup`) before anything else. APS/internal executors get per-class retry with backoff.

**P-GW-13 — Planner/router (stage 2) is optional and post-pilot, and fails open.** A small-model classification `(discipline, data_plane, complexity)` routes cheap lookups away from the large model; on any classifier failure the request goes to the default large-model path unrouted. The regex discipline-inference in `src/utils/telemetry.ts:924-960` plus accumulated O7 events are the offline eval set for tuning it. Phase 1 has one discipline (mech/core) and ~12 users — the router earns nothing yet.

**P-GW-14 — Sub-agents = re-entrant engine with a namespace-scoped registry view (post-pilot).** `runAgent(scope: {namespaces, budget, brief, parentSession})` re-enters the same engine class with a filtered capability index and toolset, child session rows carry `parent_session_id`, and only the summary returns to the parent (generalizes the VLM stateless sub-agent pattern, §9). No separate framework; D6's "never co-resident" is enforced because a registry *view*, not a flag, is what the projection builder ever sees.

**P-GW-15 — North MCP surface serves two consumption styles from one registry.** External-loop clients (O8 interim: Claude Code; provider-hosted loops per D9) get entitled tools with full schemas over Streamable HTTP + OAuth and manage their own context; the in-house loop consumes the registry internally via Mode A. Both paths hit the identical dispatcher (guardrails, audit, idempotency cannot be bypassed by choosing a client). The second MCP server (`installer/revit-api-docs-mcp`, 5 read-only tools, `src/index.ts:5-8`, `src/tools/register.ts:8-15`) attaches as the first `executor=internal-module` registration — the lowest-risk proof of §5.1.3's "future discipline modules attach behind the Gateway."

**P-GW-16 — Telemetry: keep the interception pattern, replace the writers.** `wrapServerWithTelemetry`'s wrapping approach survives as the dispatch middleware, but the workstation-era NDJSON writers (%ProgramData% + NAS reportsRoot, `telemetry.ts:1211-1231, 1754-1762`) are replaced by a single O7 event emitter (Postgres sink Phase 1). Its existing event vocabulary (params/response summarization, spatial privacy boundary, element/document/view context extraction) is the O7 schema draft; the admin plane reads, never collects (arch §5.10).

## (d) Test strategy

1. **Freeze-baseline golden tests (regression net for the extraction).** GW-1's committed snapshot of all 35 `(name, description, JSON-schema)` triples is diffed on every CI run; any drift in tool-core during migration is a build failure. Same for the 5 docs tools.
2. **Unit:** registry collector (mixin stripping, hash stability), projection builder (purity, budget monotonicity, segment ordering), policy middleware (class × approval-state matrix), failure-taxonomy mapping, result interceptor thresholds.
3. **Contract tests:** provider layer against recorded OpenAI-compatible fixtures plus scheduled live smokes (one cloud, one local endpoint — keeps D8 honest); `RevitTransport` conformance suite executed against all three implementations (Fake always; LocalTcp on the Windows dev box in `revagent-cd` CI lane; Bridge once EXT-O1 lands).
4. **Engine E2E on FakeRevitTransport:** scripted multi-turn sessions covering Mode A discovery, confirm round-trip, gated denial, result_ref paging, loop breaker, idempotent redelivery. Deterministic (fake LLM script mode) for CI; live-LLM variants nightly.
5. **Evals:** `evals/evals.json` C#-generation cases run through the full loop (they exercise `core.code.*` prompt fidelity after instruction-doc serving); Mode A selection-accuracy eval (deferred vs preloaded control) tracked as a first-class metric with a regression threshold.
6. **Invariant gate:** 30-turn replay asserting the turn-30 ≤ 1.10 × turn-3-window token bound (GW-14) — merged as a required check before fleet cutover.
7. **Security/guardrail negatives:** cross-tenant `result_ref`/`pending_action` access, in-channel `gated` approval attempts, `WRITE_PATTERNS` bypass attempts through `core.code.execute`, north-MCP client invoking a non-entitled tool.
8. **Pilot smoke (GW-13 script):** one command that runs discovery→read→confirm-write→image-export against the pilot workstation and prints pass/fail per D11 pilot checklist.

## (e) Risks specific to this package

1. **Module-level singleton state in tool-core.** The runtime assumes one user/machine/process: telemetry session UUID + sequence counters (`telemetry.ts:55-56,145`), live-task maps, spatial-store singleton (`spatialStoreManager.ts:26-34`), per-connection framing mode. Concurrent sessions in one gateway process will cross-contaminate unless every module-level mutable is audited and moved into `InvocationContext`/session scope. *Mitigation:* GW-4 includes a grep-driven singleton audit with a lint rule banning new module-level mutable state in tool-core; spatial store becomes per-(tenant, document) instances in Phase B.
2. **Platform behavior shift Linux vs Windows.** `spatialStore` local-disk policy silently skips its drive-type probe off win32 (`spatialStore.ts:746` region), and better-sqlite3 is an exact-pinned native dep that must compile in the container. *Mitigation:* explicit Linux policy decision in GW-4 AC; container build in CI from GW-2 day one.
3. **Loose TCP response correlation is currently masked.** `SocketClient` broadcasts unmatched errors to all pending callbacks (`SocketClient.ts:223-238`); today safe only because there's one socket per call. Any gateway-side parallelism per session before O1 tightens correlation risks cross-wired results. *Mitigation:* hard one-in-flight-per-session queue in GW-7/GW-12; batching (GW-16) only after O1's correlation fix.
4. **Prompt-cache economics vs registry churn.** Any capability-index or instruction edit invalidates the S1 cache for all sessions. *Mitigation:* per-session hash pinning (P-GW-9), version rollout only at session start; measure cache-hit rate in O7 events.
5. **Mode A accuracy at today's catalog size.** Deferred loading is proven at large catalogs; at 35–40 tools an under-sized pinned set could *reduce* selection accuracy vs full preload. *Mitigation:* GW-13 measures the delta before pilot; the pinned set is registry data, tunable per discipline without code.
6. **Confirm flow through third-party MCP clients.** An external model can call any in-channel approval tool itself; elicitation support varies by client. *Mitigation:* P-GW-11's approval-URL fallback is the default for north-MCP `confirm`; `gated` is out-of-band only, always.
7. **OpenAI-compatible lowest common denominator.** The D8 contract can strand provider-specific wins (fine-grained cache control, native tool-search). *Mitigation:* capability flags per model let the adapter exploit extras behind the uniform contract; no engine logic may depend on a non-portable feature.
8. **Extraction touches the frozen old path.** GW-1 rebuilds the stdio runtime from the shared package during feature freeze; a subtle behavior change could poison the rollback path. *Mitigation:* golden-schema baseline + full `scripts/*.test.mjs` suite + Windows live smoke before any workstation ever receives a rebuilt stdio runtime (in practice none should: fleet pushes are frozen per D11, so field binaries stay untouched).
9. **Estimate risk concentrated in GW-7 and GW-14.** The engine loop and projection engine are the two genuinely novel builds (everything else is adaptation); if GW-7 slips, the pilot date slips 1:1. *Mitigation:* GW-7 starts against fakes with zero external dependencies; GW-11 and GW-15 are explicitly droppable from the pilot scope.
